Inference Benchmark Lab — Hands-on Walkthrough

Concepts, repo tour, step-by-step lab, reading results, portfolio and interview prep — plus a detailed GPU setup guide at the end.

How to use this guide

By the end you will have run a real benchmark lab and be able to answer one interview question cold: "How would you pick the fastest, cheapest way to serve model X for workload Z — and prove it?"

The code lives in the inference-bench-lab repo (on your Mac at ~/code/inference-bench-lab). Every file starts with a long comment explaining why it exists, so read the code alongside this guide.

Read it in order, like a book. Each part builds on the one before: the concepts explain what the code measures, the code tour explains what the experiments run, and the experiments give you the numbers you'll talk about in interviews. Only the reference sections at the end are meant to be dipped into when needed.

The whole lab in one picture

Think of a restaurant. The GPU is the kitchen. The inference engine (vLLM or SGLang) is the head chef deciding which orders to cook and when. Users are customers sending orders. This lab is an inspector who sends realistic customers, times every order with a stopwatch, finds the point where the kitchen falls behind, and then tries one kitchen change at a time to see which one lets it serve more customers on time.

Hardware and engine words

Term Plain English
Weights / parameters the numbers the model learned in training; an "8B" model has 8 billion of them. In BF16 each takes 2 bytes, so 8B ≈ 16 GB
Forward pass running the input once through every layer of the model; each step of prefill or decode is one forward pass
VRAM / HBM the GPU's own memory (80 GB on an H100). HBM is the type of memory; weights and the KV cache must both fit in it
Memory bandwidth how fast the GPU can read its memory (about 3.35 TB/s on an H100). It limits decode
FLOPs / compute how much math the GPU can do per second. It limits prefill
Tensor cores the parts of the GPU that do matrix math very fast; idle most of the time during decode
Arithmetic intensity how much math is done per byte read from memory. Low (decode) = memory-bound; high (prefill) = compute-bound
BF16 / FP8 / INT4 number formats: 2 bytes, 1 byte and half a byte per number. Fewer bytes = less memory and faster reads, possibly lower quality
NVLink a very fast cable between GPUs inside one server. PCIe is the slower default connection
All-reduce GPUs combining their partial results so all of them get the total; needed twice per layer in tensor parallelism (after attention and after the MLP), on every step
MoE (Mixture of Experts) a model with many small "expert" sub-networks where each token only uses a few, e.g. Qwen3-30B-A3B: 30B total, about 3B used per token
CUDA graphs the engine records the GPU work for a step once and replays it, saving launch overhead; captured at startup and during warmup
Warmup a few requests sent first and thrown away, so one-time startup costs don't distort the results
Open loop / Poisson arrivals requests arrive at random times at a set average rate, whether or not the server keeps up, like real users
Preemption the KV cache is full, so the engine pauses a request, frees its memory and redoes the work later; a sign of overload
Head-of-line blocking one big job at the front makes everyone behind it wait (e.g. a long prefill freezing other users)

More terms you'll meet later

  • OpenAI-compatible API: the request/response format OpenAI's API uses (/v1/chat/completions, /v1/models). vLLM and SGLang both speak it, so one client works with both.
  • SSE streaming: Server-Sent Events, the way the server sends tokens one at a time over one HTTP connection. Streaming is what lets us measure TTFT and ITL.
  • Process group: the set of processes (one per GPU) that work together on one model under tensor/pipeline parallelism. If one crashes, the whole group must restart.

  • Disaggregated serving: running prefill and decode on separate GPU pools and moving the KV cache between them over the network, so each phase can be sized and tuned separately. Covered in Project 2.

  • Dense model: every token uses all the weights (Llama, Qwen3-8B). The opposite is MoE, where each token uses only a few experts.

  • SM (streaming multiprocessor): one of the ~132 compute units on an H100. "SM active" or "SM busy" = the share of those units doing work; better than nvidia-smi's "GPU utilization", which only says something ran.
  • DCGM: NVIDIA's Data Center GPU Manager, the tool (and Prometheus exporter) that reports SM activity, memory bandwidth use and errors in production.
  • EAGLE head: a small extra network trained to read the big model's internal state and guess the next few tokens; the big model then checks the guesses in one pass.
  • AWQ / GPTQ: two common ways to compress weights to 4 bits. Dequantization overhead: the time spent converting those 4-bit weights back to 16 bits before each multiply.
  • LRU eviction: "least recently used": when the cache is full, throw out what was used longest ago.
  • Hopper / Blackwell: NVIDIA GPU generations (H100/H200 = Hopper; B200 = Blackwell). FP8 support in hardware starts with Hopper.
  • GSM8K: a standard set of 1,319 grade-school math word problems, used to check that a model still reasons correctly.

  • itl_p99: the 99th-percentile gap between consecutive tokens across all requests, i.e. the worst stalls users feel. In results.csv.

  • GuideLLM: the vLLM project's benchmarking tool for OpenAI-compatible servers; used here to cross-check the harness (Step 3) and, in Project 2, to replay real traffic traces.

  • Mooncake: the KV-cache-centric serving system behind the Kimi chatbot: a fast KV transfer engine, a shared KV cache pool (Mooncake Store), and published production traffic traces. Covered hands-on in Project 2.

Part 1 — Concepts you must own

Every optimization in this project attacks one of three GPU limits: compute (FLOPs), memory bandwidth (bytes/s from HBM), or memory capacity (GB of VRAM). Name which one before you change anything.

1.1 A request has two phases

  • Prefill processes the whole prompt in one forward pass. All prompt tokens are computed in parallel, so it is compute-bound. It produces the first output token. Long prompt → long prefill → high TTFT.
  • Decode generates the rest, one token per forward pass. Each pass reads every weight from HBM to produce one token per request, so it is memory-bandwidth-bound. The tensor cores are mostly idle.

This split explains almost everything: batching helps decode (one weight read serves many users), chunked prefill exists because the two phases fight over the same GPU, and disaggregated serving puts them on different GPUs.

In plain words. To produce any token, the GPU must read every weight of the model from its memory, about 16 GB for an 8B model. In prefill, that one big read is shared by all the prompt's tokens at once, so the GPU spends its time doing math: it is limited by compute. In decode, the same 16 GB read produces only one new token per user, so the GPU spends most of its time waiting for memory: it is limited by memory bandwidth. Picture a chef who must walk through the entire pantry before cooking each dish: cooking 500 dishes per walk (prefill) is efficient; one dish per walk (decode) is mostly walking. Batching (1.3) is cooking for many customers per walk.

1.2 The KV cache

Attention needs the Key and Value vectors of every previous token. Recomputing them each step would be quadratic, so the engine stores them: the KV cache. It grows with every token of every running request.

The words in that sentence, explained. A model is a stack of identical layers (32 in an 8B model, 80 in a 70B). Inside each layer, attention is how the model decides which earlier words matter for the next one. For every token, each layer computes three small lists of numbers: a query ("what am I looking for?"), a key ("what do I contain?") and a value ("what information do I carry?"). The new token's query is compared with the keys of all earlier tokens, and their values are blended accordingly. Attention is split into several heads that each look for different patterns; head dim is the length of each head's list (usually 128). Keys and values of earlier tokens never change, so they are stored rather than recomputed (recomputing them at every step would make the work grow with the square of the conversation length: "quadratic"). That store is the KV cache.

All the numbers in the formula below come from the model's config.json on Hugging Face: num_hidden_layers (layers), num_key_value_heads (KV heads) and head_dim (or hidden_size ÷ num_attention_heads). Bytes per value is 2 for BF16, 1 for FP8.

KV bytes per token = 2 × layers × KV heads × head dim × bytes per value

Llama-3 70B in BF16: 2 × 80 × 8 × 128 × 2 = 327,680 bytes ≈ 320 KB per token. An 8K-token request needs ~2.6 GB. The KV cache, not compute, is usually what caps your batch size. Run tools/kv_cache_calc.py until you can do this on a whiteboard.

  • GQA (grouped-query attention): many query heads share one KV head. Llama-3 70B has 64 query heads but 8 KV heads, an 8× KV saving.
  • PagedAttention (vLLM): KV is stored in fixed-size blocks like OS memory pages, so there's no fragmentation and blocks can be shared.
  • Prefix caching: if a new request starts with the same tokens as an earlier one, reuse those KV blocks and skip that part of prefill. vLLM hashes each block (Automatic Prefix Caching); SGLang keeps a radix tree of token prefixes (RadixAttention), which handles branching conversations well.

In plain words. To write the next word, the model must look back at every earlier word of that conversation. Instead of re-reading the whole conversation each time, it keeps a summary of each earlier token (its "keys" and "values") in GPU memory: the KV cache. Every active user's cache sits in the same GPU memory as the model, so memory fills up with conversations. When it's full, no more users can join the batch, however fast the GPU is. That's why most optimizations in this lab are really about using that memory better.

1.3 Batching

  • Static batching: wait for a batch, run it until the longest request finishes. Short requests waste their slot.
  • Continuous batching: the scheduler runs step by step; finished requests leave and new ones join at every step. This is the default in vLLM and SGLang and the main reason they beat naive serving.
  • The trade-off: bigger batch → more tokens/s total, but each step serves more users, so each user's TPOT rises. Why: each decode step reads all the weights once (shared by everyone) plus every running request's KV cache (one per user, growing with conversation length). Step time ≈ (weights + sum of all users' KV) ÷ memory bandwidth, so more users or longer contexts mean more bytes per step and a higher TPOT. The right batch size is the largest one that still meets the TPOT target. Batch limit flags: vLLM --max-num-seqs, SGLang --max-running-requests.
  • Chunked prefill: a 6,000-token prefill in one step freezes every decoding user for that step. Chunked prefill splits it into chunks (vLLM --max-num-batched-tokens, SGLang --chunked-prefill-size) that share each step with decodes. Smoother TPOT, slightly slower TTFT for the long request.

In plain words. Because decode is mostly "walking the pantry", serving 64 users in one step costs only a little more than serving one: the weights are read once either way. That's why batching gives so much throughput almost for free, and why the limit is usually memory (how many conversations fit), not speed. The catch: each step does a bit more work with every user added, so each user's words come a little slower (TPOT rises). The engine's job is to keep the batch as full as possible without breaking the TPOT promise.

1.4 Parallelism (splitting a model across GPUs)

Type What is split Communication Use when
Tensor parallel (TP) each layer's matrices across GPUs all-reduce after every layer — heavy inside one node with NVLink; lowers latency
Pipeline parallel (PP) groups of layers across GPUs activations passed between stages — light across nodes, or when TP communication is too slow; adds pipeline bubbles
Expert parallel (EP) whole MoE experts across GPUs all-to-all: tokens sent to their expert's GPU MoE models; bigger, more efficient matmuls
Data parallel (DP) nothing — full replicas none between replicas scale throughput once one replica meets latency

Rule of thumb: TP within a node, PP or EP across nodes, DP to add capacity. Always judge by tokens/s per GPU and $/1M tokens; doubling GPUs for 1.3× throughput is a loss.

In plain words. A 70B model in BF16 is about 140 GB, which doesn't fit in one 80 GB GPU, so it must be split. TP is like four chefs each cooking a quarter of every dish, so they must talk constantly; that only works if they stand close together (NVLink in one server). PP is an assembly line: chef 1 does the first half of the steps, chef 2 the second; less talking, but someone is often waiting ("bubbles"). DP is simply opening a second identical kitchen. EP applies to MoE models: each chef specialises in some recipes, and orders are routed to the right specialist.

1.5 Quantization

Store weights (and optionally KV) in fewer bits: BF16 (2 bytes) → FP8 (1 byte) → INT4 (0.5 byte).

  • Decode reads every weight each step, so half the bytes ≈ up to 2× faster decode.
  • Freed memory becomes KV cache → bigger batches.
  • FP8 on Hopper/Blackwell also uses FP8 tensor cores → faster prefill.
  • A 70B model in FP8 fits on 2× H100 instead of 4×. Why 4 in BF16 and not 2 or 3: its 141 GB of weights don't fit in 2 × ~68 GB of usable memory (after leaving room for overhead, and none would be left for the KV cache), and tensor parallelism must divide the model's attention heads evenly (64 query heads, 8 KV heads), so 3 GPUs isn't allowed. In FP8 the weights are ~71 GB, so 2 GPUs work. That halves cost if quality holds.
  • Always measure quality too (e.g. lm-evaluation-harness). Speed without an accuracy check is not a result.

In plain words. Quantization stores each weight with fewer bytes, like saving a photo at lower quality. Since decode is limited by how many bytes the GPU must read, half the bytes means roughly twice as many "pantry walks" per second, and the freed memory holds more conversations. The risk is the same as with a lower-quality photo: some detail may be lost, so the model's answers may get slightly worse. That's why every quantization result must come with a quality score.

1.6 Speculative decoding

A cheap drafter (an EAGLE head, a small model, or n-gram lookup from the prompt) guesses k tokens. The big model verifies all k in one forward pass and keeps the ones it agrees with. Because decode is bandwidth-bound, verifying k tokens costs about the same as generating one.

  • Helps at low load, when the GPU has spare compute.
  • Can hurt at high load: the GPU is already busy, and rejected guesses are wasted work.
  • The speedup depends on the acceptance rate, which depends on the text. Synthetic prompts give fake acceptance rates; use real prompts for this experiment.

In plain words. An apprentice quickly guesses the next few words; the head chef checks all the guesses in one go and keeps the correct ones. When the kitchen is quiet, checking costs little extra, so several words come out per step: faster. When the kitchen is packed, the chef has no spare time, and every wrong guess is wasted effort: slower. And the apprentice guesses well only on predictable text, so you must test with real prompts.

  • An SLO is a latency target from the product, e.g. p90 TTFT ≤ 1 s and p90 TPOT ≤ 50 ms (50 ms = 20 tokens/s, faster than people read).
  • In one line: the headline number is capacity at SLO: the highest load that still meets the targets. The next section explains both properly.
  • Cost per 1M tokens = (GPUs × $/GPU-hour) ÷ (tokens/s × 3,600) × 1,000,000. This is how you turn engineering into a number a client pays for.

p50, p90, p99: what they mean and why they matter

A percentile tells you how slow a request was compared with all the others. Line up every request's latency from fastest to slowest:

Percentile Meaning What it describes
p50 (the median) half the requests were faster, half slower the typical experience
p90 9 in 10 were at least this fast; the slowest 1 in 10 were slower the bad-but-common case
p99 99 in 100 were at least this fast; only 1 in 100 was slower the worst experience you regularly deliver

An example. 100 chat requests have these TTFTs: 80 take about 0.3 s, 15 take about 0.8 s (they arrived while a long prompt was being prefilled), and 5 take about 4 s (they queued behind a burst). Then p50 is 0.3 s, p90 is about 0.8 s and p99 is about 4 s. The average is about 0.56 s, which describes nobody, and it hides the people who waited 4 seconds.

Why they matter:

  1. The average lies. A few very slow requests drag it up, while big improvements for most users barely move it. Percentiles show the shape: p50 is the normal case, p90/p99 the bad ones.
  2. The tail is what users remember. Someone sending 20 messages a day will likely hit your p90 twice and your p99 now and then. If p99 is 4 s, they've seen your product "freeze" this week.
  3. The tail grows with fan-out. A page or agent that makes 10 model calls and waits for all of them is as slow as the slowest one. The chance that at least one of the 10 hits a p99-slow response is about 10%, so for agents your p99 becomes their typical case.
  4. The tail warns you first. As load rises, p50 stays flat for a long time while p90 and p99 start climbing: that's the knee you'll find in Step 3. The tail shows queues forming before the median does.
  5. Each percentile points to a different cause. p50 is mostly the model and the hardware. p90/p99 are mostly interference and queueing: someone else's long prefill landing in your step, batch limits, KV cache pressure. That's why chunked prefill (Step 8) barely moves p50 but can cut the p99 gap between tokens a lot.

How they're used. SLOs are written on a percentile ("p90 TTFT ≤ 1 s"): p90 is common for capacity planning, p99 for latency-critical products, and the higher the percentile the more spare capacity the promise costs. Report several together (p50, p90, p99), never one alone: a config that improves p50 but worsens p99 may be a bad trade.

Three traps:

  • You need enough requests. p99 from 100 requests rests on the single slowest one, which is noise. Aim for at least a few hundred requests per rate before trusting p99; that's why each experiment runs for minutes and sets min_requests (100 in most configs). At 4 req/s a 120 s run collects about 480 requests; at the lowest rates, treat p99 with caution.
  • Never average percentiles. The p99 of two servers isn't the average of their p99s: combine the raw latencies, then compute the percentile.
  • Watch for coordinated omission. If the load tool waits for each response before sending the next request, a slow server makes it send less, which hides the tail. This harness uses open-loop arrivals (requests arrive on schedule no matter how slow the server is) for exactly this reason.

In one interview sentence: "p50 is the typical user, p99 is the unlucky one; averages hide the unlucky one, the tail is where queueing and interference show up first, and every SLO I set or measure is a percentile at a stated load."

What an SLO is, and why it matters

An SLO (Service Level Objective) is a speed promise written as numbers, for example: "9 out of 10 requests see their first word within 1 second, and 9 out of 10 stream at least 20 tokens a second (about 15 words)." In this guide's notation that's p90 TTFT ≤ 1 s and p90 TPOT ≤ 50 ms. Every SLO has three parts:

  1. A metric: what you measure (TTFT, TPOT, or total time E2E; this lab's harness checks TTFT and TPOT).
  2. A limit: how slow is still acceptable (1 s, 50 ms).
  3. A percentile: how many requests must meet it (p90 = 90%, p99 = 99%).

The numbers come from the product, not from the engineer. The question behind them is: how long will this user wait before they decide it's broken? An SLA (Service Level Agreement) is different: it's the contract with a customer, with penalties if it's broken. Teams set the SLO stricter than the SLA so they have a safety margin.

Why it matters (four reasons, each one you can say in an interview):

  • It stops you cheating on throughput. You can always raise tokens/s by packing more users into each batch; each user simply waits longer. Without an SLO, "faster" has no meaning. With one, the question becomes how much load can we take while still keeping the promise? That's capacity at SLO, the headline number of every experiment here. You'll see this yourself in Step 3: on the mock server, chat at 16 req/s makes 2,232 tok/s, more than at 8 req/s, but p90 TTFT is 6.6 s, so it fails. 8 req/s is the highest tested rate that passes (Step 3 estimates the true limit at about 9; your laptop's numbers will differ a little).
  • It sets the GPU bill. Capacity at SLO decides how many requests one GPU can serve, which decides how many GPUs you buy. A stricter SLO means fewer users per GPU and more GPUs. This is how an inference audit turns into money: "you meet your SLO at 8 req/s per GPU; after these changes, at 12."
  • It decides which optimization wins. Chunked prefill, quantization, speculative decoding and disaggregation all trade TTFT against TPOT against throughput. Whether a trade is good depends on which limit you're closest to breaking. There's no "best config" without an SLO.
  • It's about the unlucky users, not the average. The mean hides the 1 in 10 users who waited 5 s, and they're the ones who complain or leave. Servers also get worse at the tail first: when load rises, p90 jumps long before the median (p50) moves. That's why SLOs use p90 or p99.

Which workload needs the fastest response? It depends on who is waiting and for what. (The five workloads are explained in Part 2; in short: chat = short prompts, rag = long one-off documents, agent = a long prefix shared by many requests, mixed = 80% chat + 20% rag, file = your own real prompts.)

Workload Who is waiting What matters most Typical SLO (p90)
chat a person watching the screen first word fast, then a steady stream at reading speed TTFT ≤ 0.5–1 s, TPOT ≤ 50 ms
rag a person who sent a long document with the question first word, but with some slack: reading a 3,000–7,000-token prompt (prefill) takes real time, and people accept a short pause TTFT ≤ 1–2 s, TPOT ≤ 50 ms
agent a program making many calls in a row total time per call, because each step waits for the one before: 10 steps × 3 s = 30 s for the user ideally a limit on total time per call (e.g. p90 E2E ≤ 3 s); this harness only checks TTFT and TPOT, so experiments 01 and 03 use the chat SLO (1 s / 50 ms) as a stand-in
mixed all of the above at once the strictest group in the mix (usually chat) use chat's SLO
file whoever your real prompts come from the same as the traffic it copies (experiment 07, which you switch to file for real numbers, tightens TPOT to 30 ms because speculative decoding is about TPOT) depends on the file
offline batch (not a workload here) nobody throughput and cost per token none, or "done by morning"

So: chat needs the fastest first response (a person is staring at the screen), and agents need the fastest total response (delays add up across steps). That's why most experiments here use the chat SLO (1 s / 50 ms), Experiment 04 (chunked prefill on mixed) and the 70B experiments (05, 06) relax TTFT to 2 s: long prefills queued behind each other, or a 70B model's slower prefill, would fail a 1 s target before anything interesting happens. 05 and 06 also relax TPOT to 60 ms, and experiment 07 tightens TPOT to 30 ms.

In plain words. An SLO is the restaurant's promise: "starters within 10 minutes for 9 tables out of 10." Without it, the kitchen could seat 200 people and call it a success while everyone waits an hour. With it, the real question is how many tables you can seat and still keep the promise. That number tells the owner how many chefs to hire.

What happens in one run

  1. run.py reads the YAML and, for each config, starts the server with Server(...).
  2. For each workload it sends a warmup set (different seed, results thrown away) to trigger CUDA graph capture and fill the prefix cache.
  3. For each request rate, loadgen fires about rate × duration_s requests with Poisson spacing. client records TTFT, ITL, TPOT and token counts per request while GpuMonitor samples the GPUs.
  4. metrics.summarize turns those into one row: percentiles, throughput, goodput, SLO pass/fail, $/1M tokens.
  5. If a rate is hopelessly overloaded (p90 TTFT over 10× the SLO, or more than 20% failures), higher rates are skipped to save GPU hours.
  6. The server is killed and the next config starts.
  7. analyze.py reads results.csv and finds, per config and workload, the highest rate that met the SLO.

Words in that list, explained.

  • Warmup / CUDA graph capture: the first few requests to a fresh engine are slow, because it's still compiling and recording GPU work ("capturing CUDA graphs") and its caches are empty. Measuring them would make every engine look worse than it is, so they're sent first and thrown away.
  • Poisson spacing: real users arrive randomly, not on a metronome. At 4 req/s the average gap is 250 ms, but some gaps are 20 ms and some are 900 ms. Poisson is the standard way to model that randomness, and the bursts it creates are what fill up queues.
  • Open loop vs closed loop: in an open loop the next request is sent on schedule even if earlier ones haven't finished, like real users who don't know about each other. A closed loop ("keep 32 users busy, each waits for its answer before asking again") automatically slows down when the server is slow, so it hides overload. That's why this harness is open loop.
  • perf_counter: Python's high-precision stopwatch. Unlike the wall clock, it never jumps when the system clock is adjusted, so time differences are always correct.

How to compare these predictions with what you'll measure

The calculator talks about how many requests fit at once and single-user speed; the experiments report requests per second. Two bridges connect them:

  1. Little's law: requests in flight ≈ arrival rate × time each request spends in the system. Example (70B on 4× H100): RAG at 3 req/s with 3 s end-to-end latency means about 3 × 3 = 9 requests in flight. RAG prompts average ~5,200 tokens, and about 77 requests of that length fit in KV memory, so memory is far from the limit. But also check compute: prefill work = rate × prompt length = 3 × 5,200 ≈ 15,600 tokens/s, against a best-case prefill of ~28,000 tokens/s from the calculator. At 8 req/s that becomes ~42,000 tokens/s, more than the GPUs can do: prefill compute runs out long before KV memory, and TTFT explodes. For long-prompt traffic, check compute first; for long-answer traffic, check memory first.
  2. Percent of the bandwidth bound. The calculator's "best-case single-user decode" is the speed limit set by memory bandwidth. Measure the real single-user speed as 1 ÷ tpot_p50 at your lowest rate (light load ≈ one user at a time). Example: the calculator says 204 tok/s for Qwen3-8B on an H100; you measure tpot_p50 = 6.5 ms → 1 ÷ 0.0065 = 154 tok/s → 154 ÷ 204 ≈ 75% of the hardware limit. Real engines typically land around 60–85%.

What the baseline chat lines show: finding the knee

  1. Rates 2, 4, 8: the server keeps up. TTFT stays around 50–60 ms and throughput grows with the rate. Quick sanity check: chat answers average about 275 tokens, and 2 req/s × 275 tokens ≈ 550 tok/s, close to the 544 measured. While the server keeps up, throughput ≈ rate × average answer length.
  2. Rate 16: the knee. TTFT jumps from 59 ms to 6,601 ms. Requests now arrive faster than they finish, so they wait in a queue before starting. The server's real capacity is somewhere between 8 and 16 req/s. (Add rates 10, 12 and 14 to the YAML to find it more precisely.)

(Why TPOT stays flat even when overloaded: the server runs at most 64 requests at once (max_num_seqs), so the batch never grows past 64 and each decode step costs about the same. Extra requests wait in the queue, which shows up in TTFT instead. Step 6 explores this cap.) All the pain is in waiting to start, which is why TTFT is the number that explodes.
  4. Throughput flattens at about 2,300 tok/s. That is this server's ceiling. Sending more requests only makes the queue longer, not the output faster. This is why "maximum throughput" is misleading: you only reach it by making users wait 18 seconds.

Predict the knee by hand (then check the chart)

The mock's cost model is simple on purpose, so you can do the math yourself:

  • Prefill: 60 µs per prompt token. Decode step: 12 ms + 0.12 ms × (requests in the batch). Batch limit: 64.
  • A full batch step takes 12 + 0.12 × 64 ≈ 19.7 ms and produces 64 tokens → ~3,250 tokens/s at most. Prefill work for new requests steals some of that time, so the real ceiling is closer to ~2,500 tokens/s.
  • A chat request makes ~275 output tokens and holds a batch slot for ~275 steps × 19.7 ms ≈ 5.4 s. With 64 slots: 64 ÷ (0.0197 × 275) ≈ 11.8 requests/s.

Those two numbers disagree, and the gap is the lesson. 11.8 req/s ignores prefill; the ~2,500 tok/s ceiling includes it, and 2,500 ÷ 275 ≈ 9 req/s. So the sustainable capacity for chat is about 9 req/s, and the mock agrees: at 32 req/s it completes about 9.2 req/s. If you probe rates 9–12 you may see 10 or 11 req/s still "pass". That's a short-run effect: each rate runs only ~15 s on the mock, too short for the queue to build up fully. Longer runs (duration_s 120 on real GPUs) remove most of it. Doing this calculation before running, then explaining the gap, is the habit that makes you sound senior.

Why measured throughput sits below rate × answer length at 8 req/s. output_tok_per_s and req_per_s divide by wall_s, which includes the few seconds the last requests need to finish after sending stops. On a 15-s mock run that tail is large: at 8 req/s you send ~120 requests in 15 s, but wall_s is ~21 s, so throughput reads ~1,570 tok/s instead of ~2,200. The rule holds over the sending window; on long real runs the tail matters much less. TTFT, not req_per_s, is your reliable "the server kept up" signal.

What agent shows: the effect of prefix caching

  • Baseline fails even at 2 req/s (TTFT 1,146 ms, TPOT 52 ms). Every agent request starts with the same ~4,000-token instructions, and without prefix caching the server re-reads all of them every time. Those long prefills also slow down everyone else's decoding, which is why TPOT rises too.
  • With prefix caching, the same traffic is easy (TTFT 44 ms, TPOT 16 ms). About 96% of each prompt now comes from the cache, so prefill almost disappears.
  • Now compare chat in both configs: nearly identical. Chat prompts are unique, so there is nothing to reuse. One setting, a huge gain, but only for the right traffic. That sentence is the most important lesson of this whole lab.

What mixed shows: one long prompt hurts everyone

How to read it fairly. mixed sends short chats and long RAG prompts together. Compare prefix-cache against prefix-cache+chunked: these differ in exactly one thing (chunked prefill), so any difference is caused by chunking. Look at itl_p99 (the worst pauses between tokens; it's in results.csv, not the console) at 4 and 8 req/s, where long prefills often overlap with decoding chats; there chunking should cut the spikes. At 2 req/s chunking can look worse (in one run itl_p99 went from 52 to 137 ms): with so little traffic, long prompts rarely collide with anyone, but each 2,048-token chunk still adds about 123 ms (2,048 × 60 µs) to the step it shares with decoding requests. Chunking trades a little average smoothness for fewer giant stalls, so it only pays off when collisions are common.

If you see fail > 0 at high rates

In the run above, fail=64 appeared at 32 req/s on a Mac but not on Linux. The cause was the load generator, not the server: every in-flight request needs a network socket, macOS allows only 256 open files per terminal by default, and at 32 req/s the harness needed more. Step 6 — Experiment 02: batch limits

python -m bench.run configs/experiments/02_batch_limits.yaml

The question: how many requests should the engine run in one batch?

Why it matters: this is the single most common tuning knob. Too small and the GPU sits half-idle while requests queue. Too big and every user's words come slowly, or the KV cache overflows and the engine has to pause requests (preemption).

What's compared (Qwen3-8B, 1 GPU, chat traffic, 4 → 128 req/s):

Config Setting What it means
vllm-seqs-32 --max-num-seqs 32 at most 32 requests in a batch
vllm-seqs-128 --max-num-seqs 128 at most 128
vllm-seqs-512 --max-num-seqs 512 effectively "as many as memory allows"
sglang-run-128 --max-running-requests 128 SGLang's name for the same limit

Predict first: which config hits the knee earliest? Which has the highest TPOT at high load?

What usually happens:

  • 32 hits the knee early: requests wait for one of the 32 slots, so TTFT explodes while TPOT stays low.
  • 512 keeps TTFT low longest, but TPOT keeps climbing as more users share each step, and may cross 50 ms first.
  • The best setting is the largest batch that still keeps p90 TPOT under the target. The knee chart shows it: the config whose curve stays under both SLO lines furthest to the right.

Where to look. In the server log, search for preemption messages (grep -i preempt results/02_batch_limits/*/logs/*/server.log): each one means a running request was kicked out because the KV cache was full and will have to redo its prefill. Don't use gpu_mem_frac_max to judge KV pressure: vLLM and SGLang reserve their whole memory share (~0.9) at startup, so that column reads ~0.9 whether the cache is empty or full. Use preemption counts, the KV cache usage line in the log, and TTFT instead. If grep finds nothing, your vLLM version may report preemptions only as a metric: run curl -s localhost:8000/metrics | grep -i preempt while the server is running.

Write in NOTES.md: the best batch limit for this model and GPU, the capacity at SLO it gives, and which limit (queueing, TPOT or memory) stopped the others.

Step 7 — Experiment 03: prefix caching

python -m bench.run configs/experiments/03_prefix_caching.yaml

The question: how much does reusing shared prompt beginnings help, and when does the help disappear?

Why it matters: agents, chatbots with long system prompts and RAG over the same documents all resend the same first thousands of tokens. Recomputing them every time wastes most of the GPU's prefill work. This is often the biggest single win for real products.

What's compared (Qwen3-8B, 1 GPU, agent traffic: 8 agents, each with a 4,000-token shared prefix):

Config Setting
vllm-apc-off prefix caching off (--no-enable-prefix-caching)
vllm-apc-on vLLM automatic prefix caching on
sglang-radix-off SGLang RadixAttention off (--disable-radix-cache)
sglang-radix-on SGLang RadixAttention on (its default)

Predict first: how much lower will TTFT be with caching on? Will TPOT change too?

What usually happens: caching on cuts TTFT sharply, because prefill shrinks from about 4,000 tokens to about 200, and the knee moves far right. TPOT also improves, because fewer long prefills interrupt decoding. prefix_cache_hit_rate in results.csv should be high (for vLLM it's reported because of --enable-prompt-tokens-details).

Make the cache actually overflow. First compute whether it will: number of distinct prefixes × 4,000 tokens × 144 KB per token (Qwen3-8B, BF16). At 64 prefixes that's 64 × 4,000 × 144 KB ≈ 37 GB, which still fits in the ~51.6 GB of KV memory, so you'd see no eviction. To see the cliff, add more agent entries to the YAML, each with its own label so the results stay apart, and run only the vllm-apc-on config:

workloads:
  - {name: agent, label: agent-p8,   args: {n_prefixes: 8,   prefix_tokens: 4000}}
  - {name: agent, label: agent-p64,  args: {n_prefixes: 64,  prefix_tokens: 4000}}
  - {name: agent, label: agent-p256, args: {n_prefixes: 256, prefix_tokens: 4000}}  # ~147 GB of prefixes: overflows
run: {duration_s: 120, min_requests: 100, max_requests: 4000, seed: 42, warmup_requests: 300}

Don't confuse eviction with cold misses. The first time any prefix is seen it can't be a hit. With 256 prefixes and a few hundred requests, many prefixes are seen only once or twice, so the hit rate drops even with no eviction at all. That's why warmup_requests is raised above to cover every prefix before measuring. To prove eviction is the cause, compare agent-p256 against agent-p64 at the same rate: if p64's hit rate stays high and p256's collapses, the difference is eviction.

Engine notes. vLLM reports cache hits only with --enable-prompt-tokens-details (already in the configs). SGLang reports them only if launched with --enable-cache-report; without it, its prefix_cache_hit_rate column reads 0 even when the cache works. The mock server keeps at most 32 prefixes, so to see its cliff you'd point a copy of this YAML at the mock (as 00_mock_smoke.yaml does) and compare 8 vs 64 prefixes.

vLLM vs SGLang here: vLLM stores reusable pieces as fixed-size blocks found by a hash; SGLang keeps a tree of token sequences (RadixAttention). Both win big on this workload; differences appear with branching conversations and memory pressure.

Write in NOTES.md: capacity at SLO with caching on vs off, the hit rate, and the n_prefixes value where the gain starts to fade.

Check yourself: a client's prompts each start with the user's own unique document. Will prefix caching help them? Why?

Step 8 — Experiment 04: chunked prefill

python -m bench.run configs/experiments/04_chunked_prefill.yaml

The question: how big should the chunks be when a long prompt shares the GPU with users who are mid-answer?

Why it matters: without chunking, one 6,000-token prompt is processed in a single long step, and every user who is currently streaming an answer freezes for that whole step (head-of-line blocking). Users see the text stop for a moment. Chunked prefill cuts the long prompt into pieces and mixes them with everyone else's next words.

What's compared (Qwen3-8B, 1 GPU, mixed traffic: 80% chat + 20% long RAG; TTFT target relaxed to 2 s):

Config Setting What it means
vllm-budget-512 --max-num-batched-tokens 512 small chunks: at most 512 prompt tokens per step
vllm-budget-2048 --max-num-batched-tokens 2048 medium chunks
vllm-budget-16384 --max-num-batched-tokens 16384 huge chunks: almost like no chunking
sglang-chunk-off --chunked-prefill-size -1 chunking off
sglang-chunk-2048 --chunked-prefill-size 2048 medium chunks

Note: in current vLLM (V1 engine) chunked prefill is always on and can't be switched off, so for vLLM you compare chunk sizes (--max-num-batched-tokens 512 vs 2048 vs 16384, as in the config) rather than on vs off. SGLang can turn it off with --chunked-prefill-size -1.

Predict first: which config gives chat users the smoothest stream? Which gives RAG users the fastest first word?

What usually happens: small chunks give the lowest itl_p99 and tpot_p99 (smooth streams for chat users) but slightly higher TTFT for RAG users, because their prompt now takes several steps. Huge chunks do the opposite. Capacity at SLO may barely change; the improvement is in the worst-case freezes.

Where to look: the p99 columns (itl_p99, tpot_p99) in results.csv, not p90. This optimization protects the unlucky users.

Step 9 — Experiment 05: parallelism on a 70B model

python -m bench.run configs/experiments/05_parallelism_70b.yaml

The question: a 70B model doesn't fit on one GPU. What's the best way to split it, and is using more GPUs worth the money?

Why it matters: big models are where GPU bills get large. Choosing TP=4 vs TP=8 can double the hardware cost; the question is whether it doubles the useful output.

What's compared (Llama-3.3-70B, chat and rag, TTFT target 2 s, TPOT target 60 ms):

Config GPUs Layout
vllm-tp4 4 every layer split across 4 GPUs
vllm-tp2-pp2 4 2 pipeline stages, each split across 2 GPUs
vllm-tp8 8 every layer split across 8 GPUs
sglang-tp4 4 SGLang with every layer split across 4 GPUs

Predict first: run python tools/kv_cache_calc.py --model llama-3.1-70b --gpu h100 --tp 4 and --tp 8. How much more KV room does TP=8 give? (The calculator's llama-3.1-70b preset has the same architecture as the Llama-3.3-70B used in the experiment.) Will it serve twice as many users?

What usually happens:

  • TP=4 beats TP=2×PP=2 on latency inside one server: NVLink makes TP's constant communication cheap, while PP adds waiting ("bubbles").
  • TP=8 has lower TPOT and much more KV space, but rarely 2× the throughput of TP=4. For a 70B model in BF16, TP=8 leaves roughly 3× the KV memory (about 403 GB vs 131 GB), because the weights are the same 141 GB either way and only the leftover space grows. Compare tok/s per GPU and $/1M tok in REPORT.md: that's the number that tells you whether the extra GPUs pay for themselves. Often two TP=4 replicas beat one TP=8, because TP=8 spends more time on GPU-to-GPU communication per token, so each GPU does less useful work. Compare throughput per GPU, not total. (This harness measures one server at a time; to measure two replicas you'd need a load balancer in front of them, so here you estimate it as 2 × one TP=4 server's capacity.)
  • If your GPUs are PCIe-only (no NV# in nvidia-smi topo -m), TP communication is slow and PP may win. That's a valuable finding to explain.

Step 11 — Experiment 07: speculative decoding

The question: does guessing several words ahead make answers stream faster, and at what load does it stop helping?

Why it matters: for products where one user waits for a long answer (coding assistants, chat at quiet times), speculative decoding can cut TPOT a lot. At busy times it can make things worse. You need to know where the switch-over point is.

What's compared (Llama-3.1-8B, 1 GPU, 0.5 → 32 req/s, strict TPOT target of 30 ms):

Step 12 — Experiment 08: MoE and expert parallelism

python -m bench.run configs/experiments/08_moe_expert_parallel.yaml

The question: for Mixture-of-Experts models, is it better to split every expert across GPUs (TP) or give each GPU whole experts (EP)?

Why it matters: many of the strongest open models (DeepSeek, Qwen3 MoE, gpt-oss) are MoE. They have lots of weights in total but use only a few experts per token, so they behave differently from dense models and need different layouts.

What's compared (Qwen3-30B-A3B, 4 GPUs, chat and rag):

Config Layout
vllm-tp4 every expert split across all 4 GPUs
vllm-tp4-ep whole experts placed on different GPUs
vllm-dp4-ep 4 independent copies of the attention part, experts spread across the GPUs (each GPU holds a different subset of experts)
sglang-tp4-ep4 SGLang's expert-parallel layout

Predict first: at high load, which layout makes the biggest, most efficient matrix multiplications?

What usually happens: EP (and DP + EP) beat plain TP at high load, because each GPU works on whole experts with many tokens at once. At low load, sending tokens between GPUs to reach their expert (all-to-all communication) can make EP no better than TP.

From one server to a fleet: LeaderWorkerSet and llm-d

Everything in this lab runs one engine on one machine. Production on Kubernetes adds two problems that plain Kubernetes doesn't solve well. You don't need these to finish the lab, but you will be asked about them, and they're where Project 2 picks up.

Problem 1: one model copy that spans several machines. A 405B model, or a large MoE model with wide expert parallelism, needs more GPUs than one node has. So a single replica of the model is several pods on different nodes that must start together, know each other's addresses and ranks, and live or die together. Remember the process group from the glossary: if one member dies, the whole group is useless. A Kubernetes Deployment treats every pod as independent: one pod crashing doesn't restart its partners, and scaling adds single pods, not whole groups.

LeaderWorkerSet (LWS) is a Kubernetes API (from Kubernetes SIG Apps) that makes a group of pods the unit of replication: one leader plus N−1 workers per replica. It:

  • gives every pod its index and the leader's address through environment variables (LWS_LEADER_ADDRESS, LWS_GROUP_SIZE, LWS_WORKER_INDEX), so the engine can form its process group;
  • can restart the whole group when any pod in it fails;
  • rolls out updates one group at a time;
  • can keep a group's pods inside the same topology (for example the same rack or network block), so cross-node traffic stays fast;
  • scales by whole groups, including with the Horizontal Pod Autoscaler.

The vLLM docs show the classic example: Llama 3.1 405B as one LWS replica of 2 pods × 8 GPUs, with TP=8 inside each node and PP=2 across the two nodes. The leader runs vllm serve and serves the API; the worker runs the same command with --headless. That is exactly Step 9's rule ("TP inside a node, PP across nodes") turned into a Kubernetes object.

Problem 2: many replicas behind one endpoint. A normal Kubernetes Service spreads requests round-robin. For LLMs that wastes capacity: it ignores which replica already has a prompt's prefix in its KV cache (Step 7) and how long each replica's queue is (the knee, Step 3). Send an agent's request to the wrong replica and you pay the full 4,000-token prefill again.

llm-d is a Kubernetes-native distributed inference stack (a CNCF Sandbox project) that runs vLLM, SGLang and other engines across a cluster and adds the layer above them: routing by predicted latency, prefix-cache-aware routing, a tiered prefix cache, prefill/decode disaggregation, wide expert parallelism for MoE, flow control and fairness, and autoscaling. Its "well-lit paths" are tested recipes for each pattern. For replicas that span nodes (like wide expert parallelism), it builds on LWS.

How the layers fit together:

Layer Tool Problem it solves Where you met it
One engine, one machine vLLM, SGLang serve one model fast Steps 4–12
One replica across several machines LeaderWorkerSet start, restart, update and scale a multi-pod group as one unit Step 9 (TP/PP), Step 12 (EP), Project 2
Many replicas, one endpoint llm-d send each request to the best replica; split prefill and decode; autoscale Step 7 (prefix caching), Project 2

When the headline number doesn't change: check the tails

Chunked prefill on the mixed workload left capacity at SLO unchanged (4 req/s both ways). But p99 inter-token latency at 4 req/s fell from 210 ms to 138 ms, because chat users no longer froze while a long RAG prompt was prefilled. That's only visible in itl_p99 / tpot_p99 in results.csv. Lesson: some optimizations improve the worst-case user experience, not throughput, and you have to look at p99 to see them.

Three things to check before believing any result

  1. Failures: num_failed must be 0. A config that "wins" by dropping requests didn't win.
  2. Resolution: capacity can only be one of your sweep rates. If two configs both show "8", the real values could be 8 and 15. Add rates between the last pass and the first fail to sharpen it.
  3. Repeatability: run the deciding experiment three times. If the spread is bigger than the difference between configs, you have no finding yet.

About the project

"Walk me through your benchmark project." I built a harness that answers: for a given model, GPU and workload, which engine and config give the most throughput within a latency SLO, and at what cost per million tokens. It launches vLLM or SGLang from a YAML config, drives them with open-loop Poisson traffic across a sweep of request rates, records TTFT, TPOT and ITL per request from the token stream, and reports capacity at SLO. I ran eight experiments, one variable each: batch limits, prefix caching, chunked prefill, TP vs PP, quantization, speculative decoding and expert parallelism. My headline finding was [your number].

"Why open-loop load instead of fixed concurrency?" With fixed concurrency, clients wait for answers, so when the server slows down the load drops too, and queueing never shows up. Real users arrive regardless. Open-loop Poisson arrivals expose the knee where queueing makes TTFT explode, which is what capacity planning needs.

"How did you make the comparison fair?" Same requests from fixed seeds, fixed output length with ignore_eos, greedy sampling, warmup excluded, one variable per experiment, and every run saves the engine version, GPU, driver and exact launch command. I also report per-GPU throughput so a config that uses more GPUs doesn't look better just for being bigger.

"Why not just report max throughput?" Any engine hits max throughput when you overload it and let latency go unbounded. That number only matters for offline batch jobs. For interactive serving the useful numbers measure throughput while meeting the SLO. Two related terms, easy to mix up: capacity at SLO is the highest request rate at which the p90 latencies still meet the SLO (one number per config, read off the knee chart); goodput is, at one given rate, how many requests per second actually met the SLO (goodput_req_per_s in results.csv). Below the knee they're about equal to the request rate; past it, goodput falls as more requests miss.

Fundamentals

"Why is decode memory-bound and prefill compute-bound?" Prefill processes all prompt tokens in one pass, so each weight read is reused across thousands of tokens: high arithmetic intensity. Decode produces one token per request per pass, so every weight is read from HBM to do very little math. With batch 1 a 70B BF16 model on 4× H100 needs to read ~35 GB per GPU per token; at 3.35 TB/s that's ~10 ms, so ~95 tok/s is the ceiling no matter how many FLOPs you have. Batching raises the math done per byte read.

"How big is the KV cache for model X?" 2 × layers × KV heads × head dim × bytes, per token. Llama-3 70B: 2 × 80 × 8 × 128 × 2 bytes ≈ 320 KB per token, so 2.6 GB for an 8K request. GQA is why it's 8 KV heads and not 64. FP8 KV halves it.

"What limits batch size?" Usually KV cache memory, not compute: free VRAM after weights ÷ KV per request. Then latency: each extra sequence makes each decode step a bit longer, so TPOT rises. The best batch size is the largest that fits in memory and still meets the TPOT target.

"Explain continuous batching." The scheduler works per decode step instead of per batch. Finished requests leave and waiting ones join at the next step, so the GPU never waits for the slowest request in a batch. vLLM and SGLang both do this by default.

"What does chunked prefill fix?" A long prefill in one step stalls every user who's decoding, which shows up as ITL spikes and bad p99 TPOT. Chunking splits the prefill across steps that also run decodes. Smaller chunks smooth the tail but make the long request's TTFT slightly worse. The budget is a tuning knob, and I measured it on a mixed workload.

"Prefix caching vs RadixAttention?" Both reuse KV for a shared prompt prefix. vLLM's automatic prefix caching hashes fixed-size KV blocks; SGLang's RadixAttention keeps a radix tree of token sequences with LRU eviction, which handles branching conversations and many tenants well. On my agent workload caching moved capacity by [×K]; the gain shrank as I raised the number of distinct prefixes because of eviction.

"TP vs PP vs EP — when do you use which?" TP splits each layer and needs an all-reduce per layer, so it wants NVLink inside a node; it lowers per-token latency. PP splits layers into stages with light communication, so it suits crossing nodes, but has pipeline bubbles. EP places whole experts on different GPUs for MoE models, changing communication to all-to-all. Add DP replicas for capacity once one replica meets latency.

"When does speculative decoding hurt?" At high load. It trades spare compute for fewer decode steps. When the GPU is already busy with a big batch, there's no spare compute, and every rejected draft token is wasted work. Its benefit also depends on acceptance rate, which depends on the text, so you must benchmark it on real prompts. I found the crossover at about [rate] req/s.

"FP8 or INT4?" FP8 on Hopper/Blackwell has hardware support, small accuracy loss, and speeds up both prefill and decode. INT4 weight-only (AWQ/GPTQ) saves more memory and helps decode, but dequantization overhead can hurt at large batch sizes, and quality loss is larger. I'd start with FP8 and always run an eval alongside the benchmark.

"nvidia-smi says 100% utilization. Is the GPU saturated?" No. That metric means a kernel was running during the sample window, not that the SMs or tensor cores were busy. Use DCGM profiling metrics like SM active and tensor pipe active to see real utilization.

"How would you serve a model too big for one node on Kubernetes?" Split it the same way as on bare metal: tensor parallelism inside each node (NVLink), pipeline parallelism (or expert parallelism for MoE) across nodes. On Kubernetes, run each replica as a LeaderWorkerSet group: one leader and N−1 workers that start together, get their rank and the leader's address from LWS, and restart together, because the engine's process group can't survive losing a member. Then put a cache-aware router such as llm-d in front of the replicas, so requests sharing a prefix land on the replica that already has it cached instead of being spread round-robin.

"How do you know your benchmark numbers are right?" Three ways. I test the harness on a mock server whose behaviour I can calculate by hand, and check the knee lands where the math predicts. I cross-check against an independent tool, GuideLLM from the vLLM project, on the same server with the same traffic shape: TPOT agreed within 0.1 ms and TTFT within a few ms, with the difference explained by prompt length. And I check the load generator itself sends the rate I asked for; that's how I caught GuideLLM's Poisson mode over-sending. Every run also records versions, flags and the exact command, so anyone can reproduce it.

Part 7 — Answer key for "Check yourself"

Try each question out loud first. Then compare: your words can differ, but the mechanism should match.

Part 1

  1. First word slow, rest normal: the first word needs prefill over the whole prompt, which grows with prompt length. Each later word is one decode step, whose cost doesn't depend much on prompt length.
  2. Decode is memory-bound: each step reads all the weights (about 16 GB for an 8B model) to make just one token per user, so the GPU waits on memory far more than it does math.
  3. KV cache for 8,000 tokens on Llama-3 70B: 320 KB × 8,000 ≈ 2.6 GB. Each user's cache shares GPU memory with the model, so free memory ÷ 2.6 GB is roughly how many such users fit at once.
  4. Prefix caching: helps when many requests start with the same long text (system prompts, agents, repeated documents); does nothing when every prompt is unique.
  5. Double the batch: total throughput goes up (the weights are read once per step either way), but each step does more work, so each user's TPOT rises a bit, until memory runs out.
  6. One long prompt freezes others: its whole prefill runs in one step, and everyone streaming waits for that step to finish. Chunked prefill splits it into small pieces mixed into normal steps, so no single step is long.
  7. TP stays inside one server: TP needs the GPUs to exchange results after every layer; only NVLink inside a server is fast enough for that constant communication.
  8. FP8 speeds up decode: decode is limited by bytes read, not math; 1-byte weights mean half the bytes per step, so steps finish faster. Freed memory also fits more conversations.
  9. Speculative decoding hurts at high load: it uses spare GPU time to check guesses. A busy GPU has no spare time, and wrong guesses become wasted work.
  10. p90 and capacity at SLO: averages hide the users having a bad time; p90 shows what the unlucky 10% experience. Maximum throughput is only reached by making users wait forever, so it doesn't describe a usable service.

Part 2

  1. Same requests everywhere: a fixed random seed generates identical prompts, and ignore_eos forces every answer to be exactly max_tokens long, so no engine "wins" by writing shorter answers.
  2. Fixed rate, not fixed users: real users don't wait for each other. With a fixed number of busy users, a slow server automatically gets fewer requests and queueing never shows; a fixed arrival rate exposes the real breaking point.
  3. First-token timing: the client records a high-precision clock time when it sends the request and when the first streamed chunk with text arrives; the difference is TTFT.
  4. Kill the process group: multi-GPU engines start one worker process per GPU. Killing only the parent can leave workers holding GPU memory, and the next config then runs out of memory.
  5. Mock server: engine_loop admits waiting requests while there's batch room and KV space (max_num_seqs, kv_capacity_tokens), decides prefill work per step (chunked or not), and chat() looks up the system prompt's hash in prefix_cache.
  6. Debugging a bad number: (1) results.csv: is TTFT high but TPOT fine (queueing: you're past the knee) or are there failures? (2) raw/<config>__<workload>__16*.jsonl: are all requests slow, or a few huge outliers, and do the slow ones have long prompts? (3) logs/<config>/server.log: preemptions, out-of-memory warnings, or errors at that time.

Part 3 steps

  • Step 5 (which engine wins where): on chat the two are usually within a few percent, because chat is decode-bound and both run near the memory-bandwidth limit. On rag and agent the gap is usually bigger, because prefill kernels, scheduling and prefix-cache design differ between engines. So yes, expect a bigger gap for agent than chat. Your actual winner depends on versions; what matters is explaining why the gap is where it is. Practical takeaway: for mostly-chat traffic, spend effort on batch limits and cost rather than switching engines.
  • Step 6 (bigger batch, fewer users meeting SLO): more users per step means more total output, but each step gets slower; past a point, TPOT crosses the target and those users fail the promise even though throughput is higher.
  • Step 7 (each prompt starts with a unique document): no. Prefix caching only reuses identical beginnings; a unique document at the start means nothing to reuse. Putting shared instructions before the document would make them cacheable.
  • Step 8 (smaller chunks): the long prompt's prefill is now spread over more steps, so its first word comes later; in exchange, no step is long enough to freeze the other users.
  • Step 9 (8 GPUs, 1.4× throughput): you pay 2× for 1.4× the output, so cost per token rises about 43%. Two separate 4-GPU copies would usually give close to 2×.
  • Step 10 (fewer bytes, same math): decode time is mostly spent reading weights from memory; half the bytes means half the reading time per step.
  • Step 11 (busy all day): probably not. First measure TPOT with and without speculation at their actual load, on their real prompts, and check the acceptance rate.
  • Step 12 (MoE memory): every token may be routed to any expert, so all experts must be loaded in GPU memory at all times, even though each token uses only a few.

Part 4

  1. Curve moves right: more throughput at the same latency (more capacity). Moves down: lower latency at the same throughput (better experience).
  2. Capacity is a tested rate: the harness only knows rates it tried. Add rates between the last pass and the first fail (e.g. 10, 12, 14 between 8 and 16) to narrow it down.
  3. Prefix caching on agent vs chat: agent prompts share a long identical beginning that can be reused; chat prompts are all different, so there's nothing to reuse.
  4. Chunked prefill's benefit: in the tail latency columns, itl_p99 and tpot_p99 in results.csv, which show shorter worst-case freezes for streaming users.

Troubleshooting

Every config writes logs/<config>/server.log and server_cmd.txt; read the log first.

Symptom Likely cause Fix
CONFIG FAILED: server exited early unknown flag for your engine version, or OOM while loading check the log; run $VLLM_BIN serve --help / $SGLANG_PYTHON -m sglang.launch_server --help; lower --gpu-memory-utilization or --max-model-len
Next config OOMs right after a previous one old worker processes still hold VRAM nvidia-smi to find them; raise cooldown_s in the config; the harness kills the process group, but a crashed engine can leave orphans
TimeoutError: server not ready first-time model download or slow disk pre-download with huggingface-cli download; raise ready_timeout_s
HTTP 400 on every request prompt + max_tokens exceeds --max-model-len, or an unsupported field raise max model length or shrink the workload ranges
HTTP 401/403 downloading the model gated model accept the licence on Hugging Face; set HF_TOKEN
prefix_cache_hit_rate is 0 with caching on engine doesn't report cached tokens vLLM: add --enable-prompt-tokens-details; SGLang: launch with --enable-cache-report (Step 7)
TPOT looks impossibly low several tokens arrive in one chunk (normal with speculative decoding) TPOT already uses the server's token count; check itl in the raw JSONL
Latency high but GPU utilization low bottleneck outside the GPU: CPU, tokenizer, the load generator run the client on another machine; check CPU usage; if you set a cap, raise or remove max_concurrency
Results vary run to run thermal throttling, other jobs on the node, too-short runs lock the node; raise duration_s; repeat the run 3 times and report the spread

On a Mac, fail > 0 only at high rates: usually the load generator running out of network sockets ("Too many open files"), not the server. The harness raises the limit automatically; if failures persist, run ulimit -n 4096 in the same terminal first. See Step 3, "If you see fail > 0 at high rates".

  • Server takes too long to start or needs a pause between configs: ready_timeout_s and cooldown_s are set per config in the experiment YAML (inside each entry under configs:), not globally.
  • A flag isn't recognized: flags differ between versions; list the ones your install supports with $VLLM_BIN serve --help (or $SGLANG_PYTHON -m sglang.launch_server --help).
  • Too many requests in flight on a small machine: max_concurrency under run: caps how many requests the load generator keeps open at once. It's unlimited by default, which is what open-loop testing wants; only set it if your client machine can't keep up.

GPU setup guide

From "I can log in to a GPU machine" to "my first real benchmark finished". Every command explained.

This tab takes you from "I can log in to a GPU machine" to "my first real benchmark finished". Every command is explained. Do the steps in order and don't skip the checks.

Before you start

Words you'll see

Word What it means in plain English
GPU The graphics card that does the AI math. An H100 is one GPU. A server often holds 8.
VRAM / HBM The GPU's own memory (80 GB on an H100). The model and the KV cache must fit here.
Driver Software that lets Linux talk to the GPU. Without it, nothing works.
CUDA NVIDIA's toolkit for running programs on the GPU. vLLM and SGLang bring their own copy; you mostly need a new enough driver.

SSH How you log in to a remote computer from your Mac's Terminal.
tmux Keeps your programs running on the server after you close your laptop.
venv A private folder of Python packages, so vLLM and SGLang don't break each other.

Hugging Face The website where open models (Llama, Qwen) are downloaded from.

What you need

  • A Linux GPU machine you can log in to (usually Ubuntu), with its address (like 10.1.2.3 or gpu01.example.com) and your username. This guide assumes a plain server or cloud VM. If your GPUs are only reachable through Kubernetes or OpenShift, read that section near the end first.
  • Permission to use it for this project. If the GPUs belong to your employer, check that personal or portfolio work on them is allowed, and that you may publish the results. Publishing numbers from company hardware without permission can cause real trouble. A rented cloud GPU (RunPod, Lambda, a GCP or Azure VM) avoids the question completely.
  • Free disk space: at least 200 GB for the 8B experiments, 500 GB+ if you'll run 70B models.
  • The code on your Mac at ~/code/inference-bench-lab (already done).
  • About 2–3 hours for the first full setup.

In the commands below, a line starting with # is a comment explaining the line; you don't need to type it (pasting it is harmless). Each code box starts with a comment saying where to type it: # ON YOUR MAC (the Terminal app on your Mac) or # ON THE GPU MACHINE (after you've logged in with SSH).

Step 1 — Connect to the GPU machine

1a. Make an SSH key (once, on your Mac)

An SSH key is like a house key for servers: safer than typing a password every time.

# ON YOUR MAC
ls ~/.ssh/id_ed25519.pub          # if this prints a file name, you already have a key: skip the next line
ssh-keygen -t ed25519 -C "you@mac"   # press Enter to accept the defaults; a passphrase is optional
cat ~/.ssh/id_ed25519.pub         # prints your PUBLIC key (safe to share). Never share the file without .pub

Give the public key to whoever runs the GPU machine (or paste it into your cloud provider's "SSH keys" page).

1b. Log in

# ON YOUR MAC — replace with your real username and address
ssh you@gpu01.example.com

The first time it asks "Are you sure you want to continue connecting?" — type yes. When the prompt changes to something like you@gpu01:~$, you are on the GPU machine. Type exit to leave.

Shortcut: so you can type ssh gpu instead, add this to ~/.ssh/config on your Mac:

# ON YOUR MAC: open the file with  nano ~/.ssh/config , paste, then Ctrl-O Enter Ctrl-X to save
Host gpu
    HostName gpu01.example.com
    User you
    # keeps the connection from dropping when idle (ssh config comments must be on their own line)
    ServerAliveInterval 60

1c. Use tmux so nothing dies when you disconnect

Benchmarks run for hours. If your laptop sleeps, a normal SSH session dies and kills your benchmark with it. tmux keeps a session alive on the server.

# ON THE GPU MACHINE
sudo apt-get install -y tmux      # skip if `which tmux` already prints a path, or if you don't have sudo
tmux new -s bench                 # start a session called "bench"

The tmux keys you need (press Ctrl-b, let go, then the next key):

Keys What it does
Ctrl-b then d detach: leave everything running and go back to the normal shell
Ctrl-b then % split the screen left/right (two terminals side by side)
Ctrl-b then arrow key move between the split panes
tmux attach -t bench come back to your session later, even from a new SSH login

Try it now: run tmux new -s bench, detach with Ctrl-b d, then tmux attach -t bench. If you're back where you were, you're ready.

Step 2 — Look at the machine before touching anything

You're a doctor taking a patient's vitals. Five commands, about five minutes. Write every answer into a file called NOTES.md; these facts go at the top of every benchmark report.

2a. The GPUs: nvidia-smi

# ON THE GPU MACHINE
nvidia-smi

You'll see a table. Here's what each part means:

What you see What it means What to write down
Driver Version: 570.xx version of the NVIDIA driver the number; vLLM/SGLang need a recent one (Step 3)
CUDA Version: 12.x the newest CUDA this driver supports (not what's installed) the number
NVIDIA H100 80GB HBM3 (one row per GPU, numbered 0, 1, 2…) GPU model and its index model and how many
1MiB / 81559MiB memory used / total on that GPU should be near 0 used before you start
0% under GPU-Util how busy the GPU is should be 0% before you start
Processes: table at the bottom programs using the GPUs right now should say "No running processes found"

If another person's program is already using some GPUs, don't use those ones. Later you'll choose which GPUs to use with CUDA_VISIBLE_DEVICES. Benchmarking on a busy GPU gives wrong numbers anyway.

A nice trick: watch -n 1 nvidia-smi refreshes every second. Leave it running in a second tmux pane while benchmarks run. Ctrl-C stops it.

2b. How the GPUs are connected: nvidia-smi topo -m

# ON THE GPU MACHINE
nvidia-smi topo -m

This prints a grid: each GPU against each other GPU. Look at the boxes between two different GPUs:

  • NV18, NV12, NV4 (any NV + number): connected by NVLink. Fast. Tensor parallelism (TP) will work well.
  • PIX, PXB, PHB, NODE, SYS: connected only through the normal PCIe bus. Much slower. TP across these GPUs will be slow; this changes your results in experiment 05.

Write down "NVLink: yes/no".

2c. Disk, memory, CPU, operating system

# ON THE GPU MACHINE
df -h ~                 # disk: look at "Avail" for your home folder. Need 200 GB+ (500 GB+ for 70B models)
df -h                   # all disks: is there a big fast one (often /data, /mnt, /scratch or /raid)?
free -h                 # system RAM: look at "total". 256 GB+ is comfortable for 70B models
nproc                   # number of CPU cores
cat /etc/os-release     # which Linux, e.g. Ubuntu 22.04
which sudo && sudo -n true && echo "I have sudo"   # can you install system packages?

If your home folder is small but another disk is big (say /data has 3 TB free), you'll put models there. Make yourself a folder: mkdir -p /data/$USER. Remember that path; you'll need it in Step 5.

Step 3 — Install basic tools and check the driver

3a. Is the driver new enough?

Look at CUDA Version in the top-right of nvidia-smi (from Step 2a).

  • 12.8 or higher: good, continue.
  • 12.0–12.7: may still work, but if vLLM later fails with errors mentioning "CUDA driver version is insufficient" or "no kernel image is available", the driver is the cause.
  • 11.x or no nvidia-smi at all: stop. The driver must be installed or updated. On a shared machine, ask the administrator. On a cloud VM, it's easiest to recreate it from the provider's "GPU / Deep Learning" image, which comes with drivers installed.

Don't install or upgrade drivers yourself on a shared machine: it needs a reboot and affects everyone.

Step 7 — Serve your first model with vLLM, by hand

Before automating anything, do it once yourself so you know what "working" looks like. You need two terminals: split tmux with Ctrl-b %. The left pane runs the server; the right pane talks to it. Move between panes with Ctrl-b + arrow key.

7a. Left pane: start the server

# ON THE GPU MACHINE — LEFT PANE
cd ~/inference-bench-lab && source env.sh
CUDA_VISIBLE_DEVICES=0 $VLLM_BIN serve Qwen/Qwen3-8B --port 8000 --max-model-len 16384 --gpu-memory-utilization 0.90
#  CUDA_VISIBLE_DEVICES=0      use only GPU number 0 (pick a free one from nvidia-smi)
#  serve Qwen/Qwen3-8B         the model to load (from your Hugging Face cache)
#  --port 8000                 the "door" the server listens on
#  --max-model-len 16384       longest prompt+answer allowed, in tokens
#  --gpu-memory-utilization 0.90   vLLM may use 90% of the GPU's memory

It takes 1–3 minutes. Watch the log scroll and find these lines (wording varies a little by version):

Log line looks like What it means
Loading weights took … / Model loading took 15.3 GiB the model's weights are now in GPU memory; ~16 GB for an 8B model in BF16
GPU KV cache size: 400,000 tokens (or # GPU blocks: …) how many tokens of KV cache fit in the memory left over. Compare with your Step 4b calculator prediction.
Maximum concurrency for 16,384 tokens per request: 24x how many maximum-length requests fit at once
Capturing CUDA graphs … vLLM records the GPU work in advance so decoding runs faster; takes some seconds
Application startup complete / Uvicorn running on http://…:8000 ready. Leave it running.

Write the KV cache size and the concurrency number in NOTES.md. If your prediction was within ~20%, you understand the memory math.

7b. Right pane: talk to it

# ON THE GPU MACHINE — RIGHT PANE
curl localhost:8000/health -i | head -1          # "HTTP/1.1 200 OK" means healthy
curl -s localhost:8000/v1/models                 # lists the model name the server uses

# Ask a question (the backslashes \ just continue the command on the next line)
curl -s localhost:8000/v1/chat/completions \
  -H 'Content-Type: application/json' \
  -d '{"model": "Qwen/Qwen3-8B",
       "messages": [{"role": "user", "content": "Explain a GPU in one sentence."}],
       "max_tokens": 100}'

You get back JSON with the answer under choices[0].message.content, and a usage part with prompt_tokens and completion_tokens — exactly the numbers the harness uses. Qwen3 may start its answer with a <think> section; that's its reasoning mode and is fine.

Now watch tokens stream one by one, which is how the harness measures TTFT and TPOT:

# ON THE GPU MACHINE — RIGHT PANE
curl -sN localhost:8000/v1/chat/completions -H 'Content-Type: application/json' \
  -d '{"model": "Qwen/Qwen3-8B", "stream": true, "max_tokens": 50,
       "messages": [{"role": "user", "content": "Count to twenty."}]}'

Each data: {…} line is one chunk arriving. The time until the first one is TTFT; the gaps between them are ITL.

7c. Look at the GPU while it runs

# ON THE GPU MACHINE — RIGHT PANE
nvidia-smi

GPU 0 shows ~90% of its memory used even though nothing is happening. That's on purpose: vLLM grabs the memory up front for the KV cache. It is not a leak.

7d. Stop it

Go to the left pane and press Ctrl-C. Wait for the prompt to come back, then run nvidia-smi again: GPU 0's memory should drop back near zero. If it doesn't, a leftover process is holding it (see "When something goes wrong").

If your GPUs are on Kubernetes or OpenShift

On many company clusters you can't SSH to a GPU server; you get GPUs by creating a pod that asks for them. The simplest approach is a long-running "workbench" pod that you log in to, then follow Steps 3c–10 inside it. (Again: make sure using the cluster for this project is allowed.)

A workbench pod

Save this as bench-pod.yaml on whatever machine you run kubectl (or oc on OpenShift) from:

apiVersion: v1
kind: Pod
metadata:
  name: bench-workbench
spec:
  restartPolicy: Never
  containers:
    - name: dev
      image: vllm/vllm-openai:latest      # comes with CUDA, Python and vLLM already installed
      command: ["sleep", "infinity"]       # don't start a server; just stay alive so you can log in
      resources:
        limits:
          nvidia.com/gpu: 1               # how many GPUs; use 4 or 8 for the 70B experiments
      volumeMounts:
        - name: work
          mountPath: /work                # put the repo AND the model cache here so they survive pod restarts
  volumes:
    - name: work
      persistentVolumeClaim:
        claimName: bench-work             # a PVC of 500 GB+; ask your admin or create one

kubectl apply -f bench-pod.yaml                  # create it (oc apply on OpenShift)
kubectl get pod bench-workbench -w               # wait until STATUS is Running; Ctrl-C to stop watching
kubectl exec -it bench-workbench -- bash         # log in, like ssh

Inside the pod (this image already includes vLLM, so in env.sh set VLLM_BIN=vllm; for SGLang it's often easier to make a second workbench pod from an lmsysorg/sglang image):

  • Work in /work, not your home folder: cd /work && git clone …, and in env.sh set HF_HOME=/work/hf-cache. Anything outside /work is lost when the pod is deleted.
  • kubectl exec sessions die when your laptop disconnects. Install tmux inside the pod (apt-get update && apt-get install -y tmux) and run benchmarks inside it.
  • Copy results out with kubectl cp bench-workbench:/work/inference-bench-lab/results ./results, or push them with git.
  • Delete the pod when you're done so the GPUs go back to others: kubectl delete pod bench-workbench. The PVC (and your models) stays.

OpenShift may refuse the pod because of security rules (an error mentioning SCC or "runAsUser"). That's an admin setting; ask the platform team which service account or SCC to use for GPU workloads.

Benchmarking a real Kubernetes deployment (vLLM behind a Service) is a different, later exercise: use a config with engine: external and url: http://<service-name>:8000, and run the harness from a pod in the same cluster. That compares platform overhead against bare metal, and leads into Project 3.

When something goes wrong

First rule: read the error message slowly, then the server log. Every harness run saves each server's log at results/<experiment>/<time>/logs/<config>/server.log. tail -50 <that file> shows the last 50 lines, where the real error usually is.

What you see What it means What to do
ssh: connect to host … Connection refused / timed out can't reach the machine check the address; are you on the company VPN? is the cloud VM running?
Permission denied (publickey) the server doesn't have your SSH key send your .pub key again (Step 1a) and check the username
nvidia-smi: command not found or NVIDIA-SMI has failed no working driver Step 3a: ask the admin, or use a GPU image on the cloud
torch.cuda.is_available() prints False PyTorch can't use the GPU driver too old for that PyTorch, or CUDA_VISIBLE_DEVICES is set to nothing
CUDA out of memory / OutOfMemoryError while starting model + KV cache don't fit, or someone else is using that GPU check nvidia-smi; pick a free GPU; lower --gpu-memory-utilization (vLLM) / --mem-fraction-static (SGLang) or --max-model-len
Address already in use / port 8000 busy a server is already running on port 8000 (often your own from Step 7) lsof -i :8000 or ss -ltnp | grep 8000 to find it, stop it with Ctrl-C in its pane or kill <PID>
GPU memory stays used after you stopped a server leftover worker processes nvidia-smi shows their PID; kill <PID>, wait 10 s, then kill -9 <PID> if still there. Only kill your own processes
401 Unauthorized / 403 / gated repo when loading a model Hugging Face token missing or licence not approved source env.sh; check the model page says you have access
No space left on device disk full, usually from models df -h, du -sh $HF_HOME/hub/*; move HF_HOME to a bigger disk (Step 2c)
unrecognized arguments: --some-flag in the server log your engine version renamed or removed that flag $VLLM_BIN serve --help | grep <word> or $SGLANG_PYTHON -m sglang.launch_server --help | grep <word>; fix the flag in the YAML
TimeoutError: server not ready from the harness model still downloading or loading slowly download models first (Step 5c); add ready_timeout_s: 3600 to that config in the YAML
SSH dropped and the benchmark stopped it wasn't running inside tmux always start runs inside tmux attach -t bench
Killed with no other message the machine ran out of system RAM (not GPU memory) check free -h; run one experiment at a time; close other programs

Still stuck? Copy the exact error plus the 30 lines before it from the log, and the command you ran, and ask me — that's enough to diagnose almost anything here.
