Disaggregated Serving over RDMA — Hands-on Walkthrough

RDMA and Kubernetes networking, prefill/decode disaggregation, multi-node serving with LeaderWorkerSet, Mooncake, and real-traffic replay: concepts, code tour, step-by-step lab, reading results and interview prep.

How to use this guide

This project answers one question with measurements: when does splitting prefill and decode onto different machines, connected by RDMA, actually beat running both on every machine — and when does the network eat the gain?

It's the advanced follow-on to the Inference Benchmark Lab. It reuses that harness, so finish at least experiment 01 there first. The code is in ~/code/disagg-rdma-lab; every file opens with a comment explaining why it exists.

This is guide 3 of 3. Read Project 1: Inference Benchmark Lab first, and the SR-IOV on Linux and Kubernetes deep dive alongside Part 1 below: it explains, with labs you can run on a laptop, everything this guide's networking rests on. The Reading Order interleaves the three.

The whole lab in one picture

Project 1 pictured the GPU as a restaurant kitchen. Now picture two kitchens in different buildings. One kitchen only does the slow first step of every order: reading the whole order and preparing the ingredients (prefill). The other only does the cooking (decode). Between them, every order's prepared ingredients (the KV cache) must be carried across the street.

  • With ordinary TCP, a waiter carries each tray by hand, through several doors, and stops to repack it at each one: slow, and the waiters (the CPUs) get exhausted.
  • With RDMA, there's a conveyor belt straight from one kitchen's counter to the other's: fast, and nobody has to carry anything.

This lab measures when two specialised kitchens plus a conveyor belt beat two ordinary kitchens that each do everything, and when carrying the trays costs more than specialising saves. The rest of Kubernetes is the building management: making sure each kitchen gets its own conveyor-belt connection (SR-IOV, Multus), and that kitchens that must work as a team start and stop together (LeaderWorkerSet).

Part 1 — Networking concepts

The whole project rests on one fact: moving gigabytes between GPUs on different machines is slow and CPU-hungry over normal TCP, and fast and nearly free over RDMA. Everything in this part explains why, and how Kubernetes gets a pod onto the fast path.

1.1 TCP vs RDMA

With TCP, sending data from GPU A on node 1 to GPU B on node 2 looks like this: GPU memory → copy to CPU RAM → kernel socket buffer (another copy) → TCP/IP stack splits it into packets → NIC → wire → the same in reverse on the other side. Every step uses CPU cycles and adds latency. At 100+ Gb/s the CPU often can't keep up, so you rarely reach line rate.

RDMA (Remote Direct Memory Access) lets one machine's NIC read or write another machine's memory directly. The application registers ("pins") a memory region once; after that, the NICs move data with no kernel involvement and no CPU copies (kernel bypass, zero copy). Result: microsecond latency, close to line-rate bandwidth, almost no CPU.

TCP RDMA
Who moves the data CPU + kernel the NICs
Copies several zero (with GPUDirect, not even through CPU RAM)
Latency tens of µs and more ~1–5 µs
Bandwidth reached often 30–60% of line rate ~90%+ of line rate
Needs any NIC RDMA NICs (e.g. NVIDIA ConnectX), and a lossless network for RoCE

1.2 InfiniBand vs RoCE

RDMA runs on two kinds of networks:

  • InfiniBand (IB): its own network with its own switches and protocol, built for RDMA, lossless by design, managed by a "subnet manager". Common in AI training clusters (e.g. 400 Gb/s NDR).
  • RoCE v2 (RDMA over Converged Ethernet): RDMA packets inside UDP/IP on ordinary Ethernet switches. Cheaper and fits existing data centres, but RDMA hates dropped packets, so switches need PFC (pause frames) and ECN (congestion marking) configured. Most "slow RoCE" stories are switch configuration.

RoCE needs the right GID index (the address type RDMA uses; RoCEv2 is often index 3). If UCX picks the wrong one, connections fail or fall back silently.

1.3 GPUDirect RDMA

Normal RDMA reads host (CPU) memory. GPUDirect RDMA lets the NIC read and write GPU memory directly over PCIe, skipping CPU RAM completely. For KV-cache transfer this is the difference between "GPU → CPU RAM → wire → CPU RAM → GPU" and "GPU → wire → GPU".

Two ways to enable it: DMA-BUF (recommended by NVIDIA; needs the open GPU kernel modules and Linux 5.12+) or the older nvidia-peermem kernel module. The GPU Operator sets either up.

It also matters where the NIC is: a GPU and NIC under the same PCIe switch talk fastest. nvidia-smi topo -m shows GPU-to-NIC distances (PIX is best, SYS is worst). Big servers have one NIC per GPU ("rail-optimised") for this reason.

1.4 SR-IOV: one NIC, many virtual NICs

A pod can't own a whole physical NIC; a node has 8 GPUs but maybe 1–8 NIC ports. SR-IOV splits one physical NIC port (the PF, Physical Function) in hardware into many VFs (Virtual Functions). Each VF looks like a real NIC with its own MAC, IP and RDMA engine, and can be handed straight to a container. No software switch sits in the data path.

On Kubernetes the SR-IOV Network Operator creates the VFs on each node, and the SR-IOV device plugin advertises them as a schedulable resource, exactly like GPUs: a pod asks for nvidia.com/sriov_rdma: 1 and gets one VF.

1.5 Multus: two network cards per pod

A normal pod gets one interface, eth0, from the cluster's CNI (Calico, Cilium, OVN…), which is great for HTTP and service discovery. Multus is a "meta-CNI" that adds extra interfaces. A pod annotated k8s.v1.cni.cncf.io/networks: rdma-net gets eth0 (normal traffic: health checks, HTTP, the proxy) and net1 (the SR-IOV VF for KV transfer). The extra network is described by a NetworkAttachmentDefinition, which the SR-IOV operator creates from our SriovNetwork. An IPAM plugin (nv-ipam here) gives net1 an address.

1.6 The NVIDIA Network Operator

Installing all that by hand on every node is error-prone. The Network Operator manages it declaratively:

  • NicClusterPolicy: which components to run (Multus, CNI plugins, nv-ipam, optionally the DOCA/OFED NIC driver).
  • IPPool: the address range for net1.
  • SriovNetworkNodePolicy: "on nodes with these NICs, create N RDMA-capable VFs called sriov_rdma".
  • SriovNetwork: "make a network rdma-net from those VFs, in namespace disagg-lab".

Think of it as the GPU Operator's twin: the GPU Operator makes GPUs schedulable, the Network Operator makes RDMA NICs schedulable.

Part 2 — Disaggregated serving concepts

Disaggregation trades a network transfer for the end of prefill/decode interference. It wins when the interference you remove costs more than the transfer you add.

2.1 The problem it solves

From Project 1: prefill is compute-bound (all prompt tokens at once), decode is memory-bandwidth-bound (one token per step). On a colocated server they share every step. When a 10,000-token prompt arrives, its prefill lands inside the same step as 100 users' next tokens, and all 100 users see a stall. Chunked prefill softens this by splitting the prompt across steps, but every step still carries some prefill work.

It also forces one configuration on two different jobs. Prefill wants big batches of tokens and maximum FLOPs; decode wants many concurrent sequences, lots of KV memory and steady step times. One GPU can't be tuned for both.

2.2 The idea

Split them:

  1. A prefill instance computes the prompt's KV cache and stops after one token.
  2. The KV cache is transferred to a decode instance, usually on another machine.
  3. The decode instance generates the rest. It never runs a prefill, so its step time is stable.

A router/proxy coordinates this: prefill first, receive a "ticket" saying where the KV lives, then decode with that ticket. You can also size the two pools independently: more prefill GPUs for long-prompt traffic, more decode GPUs for long-answer traffic (written xPyD, e.g. 2P1D).

2.3 The cost: KV transfer math

Every request ships its whole KV cache across the network, and that time lands on TTFT.

transfer time ≈ (prompt tokens × KV bytes per token) ÷ effective bandwidth + fixed overhead

For Qwen3-8B (144 KB of KV per token in BF16) on H100, from tools/kv_transfer_calc.py:

Prompt KV size Prefill time TCP ~25 Gb/s TCP ~100 Gb/s RDMA RoCE 200 Gb/s RDMA IB 400 Gb/s
2,048 302 MB ~68 ms ~153 ms ~52 ms ~14 ms ~7 ms
8,192 1.2 GB ~272 ms ~606 ms ~203 ms ~55 ms ~27 ms
14,000 2.1 GB ~464 ms ~1,034 ms ~346 ms ~94 ms ~46 ms

These are spec-sheet estimates (50% MFU, typical achievable bandwidth); your measurements will differ. What matters is the shape:

  • Transfer ÷ prefill is roughly constant across prompt lengths, because both grow linearly with tokens. The link speed sets the ratio: about 2× prefill on slow TCP, about 20% on 200 Gb/s RDMA, about 10% on 400 Gb/s IB.
  • The link saturates. At R requests/s the link must carry R × KV size. With 8K prompts (1.2 GB each), a 25 Gb/s TCP link is full at about 1.7 req/s and 200 Gb/s RDMA at about 18 req/s (the calculator's second table). Past that, requests queue on the network and TTFT explodes. But often the GPU fills first: one H100 needs about 270 ms per 8K prefill, so a single prefill GPU handles only about 3.7 req/s of them (the calculator's last line). Over RDMA, that prefill cap is usually the first limit you hit (Part 6, Cost 1); over slow TCP, the link fills first.
  • KV bytes per token is model-dependent. GQA, MLA (DeepSeek) and FP8 KV shrink it, which is why some models disaggregate much more cheaply than others.
  • Real systems reduce the cost further: transferring layer by layer while prefill is still running, and using several NICs in parallel when prefill uses TP.

The senior-level answer to "should we disaggregate?" is never yes or no. It's "for this traffic, at this SLO, on this network, here's the measured crossover point" — which is what this lab produces.

2.5 KV offload (LMCache), a related idea

Disaggregation moves KV between GPUs. KV offload moves KV between memory tiers: GPU HBM → CPU RAM → local SSD → remote storage. When the GPU's prefix cache is full, evicted entries go to CPU RAM instead of being thrown away; if that prefix comes back, it's copied back over PCIe instead of being recomputed. It helps when many long prefixes recur and don't all fit on the GPU. It does nothing for unique prompts. LMCache can also serve as the KV transport for disaggregation, but this lab uses it for offload only.

Mooncake: serving built around the KV cache

Mooncake is the serving architecture behind Kimi, Moonshot AI's chatbot. Its big idea: in large-scale serving, the KV cache is the scarce resource, not compute. So instead of treating the KV cache as something each GPU keeps privately, Mooncake treats it as data to move, share and store across the whole cluster, using the CPU RAM and SSDs that sit mostly unused next to the GPUs.

It's open source and comes as three parts you'll use in this project:

Part What it does Plain English Where you use it
Transfer Engine moves blocks of memory (GPU or CPU) between machines over RDMA, with TCP as a fallback a very fast courier between machines KV transfer for P/D disaggregation (Step 13)
Mooncake Store a distributed KV cache pool in the CPU RAM (and optionally SSD) of many machines, with a small master that tracks where each block lives a shared library of already-computed prompts shared KV pool for several replicas (Step 14)
Traces real request logs from Kimi: arrival times, prompt and answer lengths, and which prompt blocks are shared real traffic, with the text removed realistic load tests (Step 15)

How it plugs into the engines:

vLLM SGLang
P/D KV transfer MooncakeConnector (kv_producer on prefill, kv_consumer on decode) plus a proxy that understands its protocol --disaggregation-transfer-backend mooncake (SGLang's default) with sglang_router
Shared KV pool MooncakeStoreConnector (kv_both); combine with P/D through MultiConnector HiCache with Mooncake Store as the third tier (GPU → CPU → Mooncake)

Push vs pull: the one difference to remember. With NIXL (what you used in Steps 7–9 and 11), prefill finishes first and hands the proxy a "ticket"; decode then pulls the KV from the prefill GPU. With Mooncake in vLLM, the proxy sends both requests at once, tagged with the same transfer_id; decode tells prefill where to put the KV, and prefill pushes it straight into decode's memory as soon as it's computed. The proxy in this repo does both (pd_proxy.py --connector nixl|mooncake), so you can read the two flows side by side.

How Mooncake Store finds shared prompts. Each block of KV (a few hundred tokens) is stored under a hash of its tokens and of everything before it. Two requests that start with the same text produce the same hashes, so the second one finds the blocks already in the pool. That's why every vLLM instance sharing a Store must use the same PYTHONHASHSEED: vLLM starts every chain of block hashes from a root value it picks at random when the process starts, unless PYTHONHASHSEED is set, in which case the root is derived from it. Different roots give identical text different keys, so the pool fills up but the cross-instance hit rate stays at zero.

Part 3 — Architecture

One request, step by step:

harness ──1──► pd-proxy ──2: prompt, max_tokens=1──► PREFILL pod (node A)
                │  ◄── 3: ticket ────────────────────┘              │
                │                                                   │ 5: KV via net1
                └──4: prompt + ticket──► DECODE pod (node B) ◄──────┘
                                             │
harness ◄── 6: streamed answer, via pd-proxy ┘

eth0 (normal pod network): steps 1-4 and 6, health checks, handshakes
net1 (SR-IOV VF):          step 5, the big KV transfer (RDMA, or TCP on the VF)

Every pod has two interfaces. Small, latency-sensitive traffic (HTTP, health checks, the NIXL side-channel handshake) stays on eth0, the normal pod network. The only big transfer, the KV cache, crosses on net1, the SR-IOV VF, which is why changing one ConfigMap value (TRANSPORT) is enough to compare RDMA with TCP. (With TRANSPORT=tcp-podnet the KV deliberately takes eth0 instead, to measure the plain pod network.)

How one request flows (vLLM + proxy)

  1. The harness sends a streaming chat request to pd-proxy.
  2. The proxy sends a copy to a prefill pod with max_tokens: 1, stream: false and kv_transfer_params: {do_remote_decode: true}. That tells vLLM: compute the KV, keep it, don't free it.
  3. Prefill returns a normal response plus kv_transfer_params: the ticket (engine id, block ids, host, port).
  4. The proxy sends the original request plus the ticket to a decode pod.
  5. Decode contacts the prefill pod's NIXL side channel (small TCP handshake on port 5600, over eth0) to exchange metadata, then pulls the KV blocks over net1 with UCX: RDMA or TCP depending on TRANSPORT.
  6. Decode generates tokens and streams them; the proxy passes the bytes through untouched, so TTFT and ITL stay honest.
  7. The proxy records prefill_ms (step 2–3) and decode_ttfb_ms (steps 4–6 until the first byte). Switch the transport and watch decode_ttfb_ms move.

If a prefill response comes back without a ticket, the connector isn't configured: decode silently recomputes the prompt. Results look fine but you've measured the wrong thing. In NIXL mode the proxy marks every response with an X-Has-KV-Ticket header so you can check. (In Mooncake mode both requests leave at once, so the proxy can't know; there you check Mooncake's transfer counters instead, Step 13.)

Step 2 — Check the hardware (on each GPU node, needs root)

Most RDMA-on-Kubernetes failures are hardware or BIOS settings, so check these before installing anything. You need a root shell on each GPU node: use SSH if you have it, or let Kubernetes give you one with kubectl debug node/\ -it --image=ubuntu, then chroot /host (the node's own filesystem is mounted at /host). ibstat, if installed, prints the same port facts more compactly. ibv_devinfo -v | grep -E "hca_id|link_layer|state|active_mtu|active_speed|active_width"  # RoCE or IB? PORT_ACTIVE? speed?
nvidia-smi topo -m                                              # GPU <-> NIC distance: PIX/PXB good, SYS bad
cat /proc/cmdline | tr ' ' '\n' | grep -i iommu                 # SR-IOV needs IOMMU on (often intel_iommu=on iommu=pt)

Also confirm with whoever owns the hardware:

  • SR-IOV enabled in BIOS and in NIC firmware. For ConnectX this is set with mlxconfig (SRIOV_EN=1, NUM_OF_VFS=<n>) and needs a reboot. Without it, the SR-IOV operator can't create VFs.
  • ACS / PCIe settings that allow GPU↔NIC peer-to-peer (needed for GPUDirect RDMA performance).
  • Switch configuration: for RoCE, PFC and ECN on the switch ports, and an MTU matching sriov-node-policy.yaml.
  • Which port is for GPU traffic. Put its name in pfNames in sriov-node-policy.yaml; never let the policy touch the NIC the node uses for management.

Step 12 — Experiment 06: one model across two nodes with LeaderWorkerSet

The question: when one model replica has to span two nodes, how should you split it, and is it worth it compared with two independent copies on the same GPUs?

Why it matters: models like Llama 3.1 405B or DeepSeek-class MoE don't fit on one 8-GPU node, so teams must run a single replica across several nodes. On Kubernetes the standard way to do that is LeaderWorkerSet (LWS), and the way you split the model decides whether the network becomes the bottleneck. This experiment uses a 70B model, which fits on 4 GPUs, so it's affordable and directly comparable with Project 1's Step 9; the lessons carry over to the big models.

A second kind of network traffic. Experiments 01–05 moved the KV cache between prefill and decode pods (NIXL/UCX), once per request. Here the model itself is split, so NCCL (NVIDIA's GPU communication library) moves intermediate results between the halves on every step:

Split across the nodes What crosses the network How often Network sensitivity
Pipeline parallel (PP) activations at the stage boundary once per step low
Tensor parallel (TP) an all-reduce of every layer's output twice per layer (after attention and after the MLP): 160 times per forward step for an 80-layer 70B, once per step for the whole batch very high

How LWS runs it. deploy/lws/vllm-tp4-pp2.yaml defines one group of 2 pods:

  • vllm-lws-0, the leader (index 0): runs the first half of the model and serves the OpenAI API on port 8000;
  • vllm-lws-0-1, the worker (index 1): runs the second half with --headless (no API).

LWS gives every pod three environment variables, and the YAML passes them straight to vLLM: LWS_GROUP_SIZE → --nnodes (how many nodes), LWS_WORKER_INDEX → --node-rank (which one am I), LWS_LEADER_ADDRESS → --master-addr (where to meet). restartPolicy: RecreateGroupOnPodRestart restarts both pods if either fails, and pod anti-affinity forces one pod per node. The wrapper deploy/common/lws-scripts.yaml (nccl-start.sh) turns the same TRANSPORT setting you used before into NCCL settings: RDMA on net1, TCP on net1, or TCP on the pod network.

What's compared (Llama-3.3-70B, always 8 GPUs = 2 nodes × 4, chat and rag):

Scenario Layout Cross-node traffic
dp2-tp4 (baseline) 2 independent replicas, TP=4 inside each node (a plain Deployment) none
lws-tp4-pp2-rdma 1 replica: TP=4 in each node, PP=2 across, NCCL over RDMA light
lws-tp4-pp2-tcp same, NCCL over the pod network light, over TCP
lws-tp8-cross-rdma 1 replica: TP=8 spanning both nodes, NCCL over RDMA heavy
lws-tp8-cross-tcp same, NCCL over TCP heavy, over TCP

Step 14 — Experiment 08: Mooncake Store, a KV cache shared by two replicas

The question: when two replicas sit behind a load balancer, how much does a shared KV cache pool help compared with each replica keeping its own?

Why it matters: a round-robin load balancer sends requests with the same prefix to every replica, so each replica computes every popular prefix again, and evicted prefixes are recomputed from scratch. A shared pool in CPU RAM fixes both, without changing the router. (llm-d's cache-aware routing attacks the same problem from the other side: send each request to the replica that already has its prefix. Both are valid; this experiment measures the pool.)

What's compared (Qwen3-8B, 2 replicas on 2 nodes, exact round-robin via deploy/mooncake/rr-proxy.yaml):

Scenario What each replica has
nostore-2x its own GPU prefix cache only
store-2x its GPU cache plus a shared Mooncake Store pool: each replica gives 48 GB of CPU RAM, ~96 GB total

Two workloads: agent-96x6k (96 agents × 6,000-token prefixes ≈ 576K tokens: more than one GPU's ~350K-token KV cache, so GPU caches thrash) and agent-8x6k (fits easily: the control, where the pool should make no difference).

How it's wired: deploy/mooncake/master.yaml runs mooncake_master (metadata only: which block lives where). Part 6 — Reading results: where the gains appear and disappear

In the local demo (simulated GPUs and network, 2 GPUs per scenario, mixed traffic with 25% long RAG prompts, SLO p90 TTFT ≤ 1 s and p90 TPOT ≤ 40 ms), disaggregation over the fast link cut p90 TPOT by about a quarter (16.6 ms vs 22.5 ms at 8 req/s) and almost removed the worst stalls (p99 gap between tokens 18 ms vs 232 ms), but lowered capacity at SLO from 12 to 8 req/s: a single prefill GPU became the bottleneck and pushed TTFT over the target. Over the slow link it missed the TTFT target at every rate. And chunked prefill didn't improve average TPOT at all, for a reason worth understanding. These are mock numbers that only prove the pipeline works, but these effects are the ones to look for on real hardware.

A lesson about the rate grid. An earlier version of this run tested only 4, 8 and 16 req/s, and colocated and disaggregated looked equal: both passed at 8 and failed at 16. Adding 10 and 12 req/s showed that colocated holds the SLO up to 12 and disaggregated only up to 8. Before you call two configurations equal, add rates around the knee.

Gain 1: decode is no longer stalled (TPOT)

Both disaggregated lines sit well below the colocated ones and stay nearly flat as load rises, because the decode GPU never runs a prefill. Colocated TPOT climbs and crosses the 40 ms target between 12 and 16 req/s (about 2,500 tok/s). The tail shows it even more clearly: at 8 req/s the p99 gap between two tokens (ITL) is 232 ms colocated, when a long prompt's prefill lands in the same step, and 18 ms disaggregated. If your product's SLO is about smooth streaming (TPOT, p99 ITL), this is the gain disaggregation buys.

Why chunked prefill didn't help average TPOT here

colocated-2x-chunked splits every prompt into pieces of 1,024 tokens. At 8 req/s its p90 TPOT is the same as plain colocated (22.6 vs 22.5 ms) and its p90 TTFT is worse (443 vs 344 ms), but its p99 ITL drops from 232 ms to 66 ms. Three reasons:

  • The mock charges every prefill token the same, wherever it lands. A 6,000-token prompt adds about 300 ms to the decode steps whether it's one 300 ms step or six 50 ms steps. TPOT is an average over the whole answer, so the same total stall gives the same TPOT. Chunking only spreads the stall out, and that is exactly what p99 ITL measures.
  • The long prompt itself waits longer. Each of its chunks shares a step with every decoding user, so it pays the decode step time (12 ms or more) once per chunk, and its TTFT rises.
  • On a real GPU chunking does better than this. A decode step is limited by memory bandwidth and leaves most of the GPU's compute idle, so a small prefill chunk can use that idle compute almost for free. The mock doesn't model that overlap, so it shows chunking's cost (TTFT) and its smoothing (p99 ITL) but not its throughput gain. That's a limit of the simulator, and a good interview point: the model of the system decides which effects you can see.

Cost 1: the prefill pool can become the bottleneck (TTFT)

With 1P1D, every prompt goes through one prefill GPU instead of being spread over two, so TTFT rises earlier than colocated. Disagg-RDMA's p90 TTFT is 939 ms at 8 req/s and 1,024 ms at 10, just over the 1 s target, while colocated stays around 300–530 ms up to 12 req/s. So capacity at SLO is lower with disaggregation (8 vs 12 req/s): the TPOT gain didn't turn into more capacity, because at this SLO TTFT runs out first. This is a P:D ratio problem, not a network problem: the prefill leg in the next chart is the same for RDMA and TCP. The fix is more prefill workers (experiment 03: 2P1D), which only makes sense when the traffic is prompt-heavy, or a product whose SLO cares more about TPOT than TTFT.

Cost 2: the network leg (RDMA vs TCP)

The proxy's TTFT split separates the two causes:

  • Prefill leg (dashed) is nearly identical for RDMA and TCP: same GPU work, same queue.
  • Decode leg (solid) is the KV pull plus the first token. Over the fast link it stays around 70–150 ms at every rate. Over the slow link it starts around 670 ms at 4 req/s and climbs to 1.5 s at 8, 4.3 s at 12 and 8.4 s at 16, because transfers queue behind each other on the shared link: link saturation.

That's the shape the calculator predicted in Part 2: on a slow link, transfer time exceeds prefill time and saturates the link at a few requests per second.

How to write the finding

Combine the views into one sentence per workload. From this mock run it would read: "With 2 GPUs on mixed traffic, 1P1D over RDMA lowered p90 TPOT from 22.5 to 16.6 ms and p99 ITL from 232 to 18 ms, but cut capacity at a 1 s TTFT target from 12 to 8 req/s, because one prefill GPU saturated; over TCP the KV transfer added 0.7–8 s and the TTFT target was never met." On your cluster, the same views will tell you whether the gain shows up, and which of the two costs eats it.

Checklist before trusting a real result

  1. X-Has-KV-Ticket: 1 on NIXL responses, or a growing mooncake_te_write_bytes_total for Mooncake (otherwise decode recomputed the prompt).
  2. Zero failures (num_failed, prefill_errors, decode_errors).
  3. Measured RDMA bandwidth (Step 5) is close to line rate, and the decode leg roughly matches the calculator.
  4. Same GPU count in every scenario you compare, and a tuned colocated baseline, behind the same kind of round-robin proxy as the disaggregated setup (the experiment files already do this).
  5. Repeat the deciding run; the spread must be smaller than the difference you report.

Answer shape: mechanism → number → trade-off → how you measured it.

The project

"Tell me about your disaggregated serving project." I built a Kubernetes lab where pods get SR-IOV RDMA NICs through the NVIDIA Network Operator and Multus, then ran disaggregated prefill/decode with vLLM's NixlConnector, SGLang and llm-d. I benchmarked every layout against a tuned colocated baseline on the same GPUs, across workloads and three KV transports — RDMA, TCP on the same NIC, and the pod network. A small proxy split TTFT into the prefill leg and the decode leg, so I could show exactly how much the network cost. My finding was [your number: e.g. disagg over RDMA held the TPOT SLO up to N req/s on mixed traffic vs M colocated; over pod-network TCP the decode leg grew X× at 8K prompts and the advantage disappeared above Y req/s].

"How did you know the difference came from the network and not something else?" Three controls. The same Deployment ran all three transports, with only one ConfigMap value changed. I measured the raw wire first with perftest and iperf3, so I knew each transport's ceiling. And the proxy timed the decode leg separately, so I could see the change land on the KV pull, not on prefill compute.

"Why not just use port-forward to benchmark?" Port-forward tunnels through the API server and my laptop. It adds jitter and caps throughput, so I'd be measuring my Wi-Fi. The load generator ran in a pod inside the cluster.

Networking

"Explain RDMA to me." The NIC reads or writes remote memory directly after the application registers it once. No kernel, no CPU copies, so microsecond latency and near line-rate bandwidth with almost no CPU. With GPUDirect RDMA the NIC accesses GPU memory directly, so KV goes GPU → wire → GPU without touching CPU RAM.

"InfiniBand or RoCE?" IB is a dedicated lossless fabric built for RDMA, common in training clusters. RoCE v2 carries RDMA over standard Ethernet; it's cheaper and fits existing networks, but needs PFC and ECN on the switches because RDMA performs badly with packet loss. Most RoCE performance problems are switch configuration or the wrong GID index.

"What do SR-IOV and Multus each do?" SR-IOV splits a physical NIC into virtual functions in hardware, so one port can serve many pods, each with its own VF and no software switch in the path; RDMA on that VF is what gives kernel bypass. The SR-IOV device plugin makes VFs a schedulable resource like GPUs. Multus lets a pod have a second interface: eth0 stays on the normal CNI for control traffic, net1 is the VF for data.

"Why did you need IPC_LOCK?" RDMA registers memory, which pins it so the OS can't page it out while the NIC is reading it. Pinning memory needs the IPC_LOCK capability (or a high memlock limit).

"NCCL, UCX, NIXL: what's the difference?" NCCL does collectives like all-reduce for tensor parallelism. UCX is a general transport layer that picks RDMA, TCP or CUDA IPC. NIXL is NVIDIA's point-to-point inference transfer library that sits on UCX and moves KV blocks. KV transfer in vLLM's NixlConnector goes NIXL→UCX, so you control it with UCX_TLS and UCX_NET_DEVICES, not NCCL variables.

Disaggregation

"When should a company disaggregate?" When traffic mixes long prompts with many decoding users and the TPOT or p99 ITL target is tight; when the network is fast relative to KV size; and when they can size prefill and decode pools to the traffic's input/output ratio. Not for short prompts, low load, or slow networks. And only after comparing against a colocated baseline tuned with chunked prefill, because that fixes part of the problem without any network.

"How big is the KV transfer, and how long does it take?" Tokens × 2 × layers × KV heads × head dim × bytes. For an 8B model with GQA that's about 144 KB per token, so an 8K prompt is about 1.2 GB. At about 22 GB/s effective on 200 Gb/s RDMA that's about 55 ms, about 20% of the prefill time; on 25 Gb/s TCP it's about 600 ms, longer than the prefill itself.

"What limits disaggregation at high load?" The link. Required bandwidth is request rate × KV per request. Past that, transfers queue and TTFT climbs. Also the P:D ratio: if prefill can't keep up, TTFT climbs even though decode is idle, which is what 1P1D typically shows on RAG-heavy traffic (say what your runs showed).

"How does the decode node know where the KV is?" The prefill response returns kv_transfer_params: engine id, block ids, host and port. The router passes that to decode. Decode does a small side-channel handshake over TCP to get metadata, then pulls the blocks over NIXL.

"What does llm-d add over a simple proxy?" An inference scheduler that picks prefill and decode pods by load and prefix-cache locality, integration with the Kubernetes Gateway API through InferencePools, and tested deployment recipes. With one prefill and one decode pod it can't do much better than round robin; with many pods and shared prefixes the scheduling matters.

"What's LMCache for?" Tiered KV storage. When the GPU prefix cache overflows, entries go to CPU RAM (or disk) instead of being dropped, and come back over PCIe when the prefix recurs — cheaper than recomputing a long prefill. It helps multi-tenant agents and long chats; it does nothing for unique prompts.

Tying it to your resume

If your resume mentions networking or multi-node performance work, expect: "Which bottleneck, how did you find it, what was the fix, what did it change?" This project gives you a measured, explainable example to fall back on: the transport comparison, the wire-level tests, and the TTFT split.

Multi-node, Mooncake and real traffic

"Why LeaderWorkerSet instead of a Deployment or StatefulSet for a multi-node model?" Because the unit that matters is the group, not the pod. A tensor- or pipeline-parallel replica spread over two nodes is one process group: both pods must start together, know their rank and the leader's address, and restart together, since the group can't survive losing a member. A Deployment treats pods as independent, so a restarted worker comes back alone and the leader hangs. A StatefulSet gives stable names, but still scales and heals one pod at a time. LWS makes "1 leader + N−1 workers" the unit it creates, updates, scales and recreates, and injects the rank and leader address. I'd split the model with TP inside each node and PP (or EP for MoE) across nodes, give the nodes RDMA, and put a cache-aware router such as llm-d in front of the replicas.

Answer to Step 12's check yourself: TP=8 inside each node over NVLink, PP=2 across the two nodes (EP for an MoE model), run as one LeaderWorkerSet group of 2 pods per replica; add replicas (more groups) for capacity; RDMA between the nodes; llm-d or another cache-aware router in front of the replicas.

"What is Mooncake, and how is it different from NIXL?" Mooncake is the KV-cache-centric serving architecture behind Kimi. Its open-source parts are a Transfer Engine, a distributed KV cache pool called Mooncake Store, and published production traces. NIXL and Mooncake's Transfer Engine both move KV between machines over RDMA; in vLLM, NIXL is pull-based (decode reads the KV after prefill finishes), while MooncakeConnector is push-based (both requests start together and prefill writes the KV into decode's memory). Mooncake Store goes further: a shared pool in the CPU RAM of many machines, so replicas reuse each other's prefixes and evicted blocks come back from RAM instead of being recomputed. I measured both libraries on the same pods and network, and the shared pool against per-replica caches with round-robin routing.

"How do you know your benchmark reflects real traffic?" Synthetic workloads with fixed shapes are good for controlled one-variable experiments. Before recommending anything, I replay real traffic shapes: Mooncake's published Kimi traces carry real arrival bursts, length mixes and prefix sharing (as block hash ids, no text), and GuideLLM replays them against any OpenAI-compatible endpoint. If the ranking of configurations holds on the trace, the recommendation stands.

Answer to Step 13's check yourself: on what hardware, network and prompt lengths; at what load (the knee, not one easy rate) and which percentile; and whether the difference is bigger than run-to-run noise, with proof that KV actually moved (mooncake_te_write_bytes_total, NIXL logs) rather than decode quietly recomputing.

Answer to Step 14's check yourself: blocks are keyed by a chain of hashes: each block's hash covers its tokens and the hash of the block before it. vLLM starts that chain from a random root value per process, unless PYTHONHASHSEED is set, in which case the root comes from it. With different roots, identical prompts produce different keys: the pool fills up, but the cross-instance hit rate stays at zero, so store-2x looks no better than nostore-2x.
