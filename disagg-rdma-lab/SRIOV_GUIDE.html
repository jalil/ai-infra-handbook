SR-IOV on Linux and Kubernetes — A Hands-on Deep Dive

From PCIe functions to pods with their own RDMA-capable NIC: the hardware, Linux by hand, a no-hardware lab, Kubernetes by hand and with the operator, performance, security, troubleshooting and interview prep.

How to use this guide

SR-IOV lets one physical network card appear as many real network cards, so each VM or pod gets its own hardware queue, with no software switch in the path. This guide takes you from "what is a PCIe function?" to running pods with their own RDMA-capable virtual NIC on Kubernetes, and being able to explain every layer in an interview.

It's written for an engineer who knows Linux and Kubernetes basics (pods, Deployments, kubectl, ip addr) but has never touched PCIe or SR-IOV. It's the deep companion to Part 1 of the Disaggregated Serving over RDMA walkthrough: that guide uses SR-IOV; this one explains it.

This is guide 2 of 3. Read it after Project 1: Inference Benchmark Lab and before or alongside Project 2: Disaggregated Serving over RDMA. The Reading Order says which parts of this guide go with which steps of Project 2.

Read it like a book

Each part builds on the one before. Parts 1–2 are concepts, Parts 3–5 are Linux, Parts 6–8 are Kubernetes, Parts 9–11 are running it well, Part 12 is interview practice. Every hands-on section ends with a Check: line; don't move on until it passes.

Next: Part 1, why SR-IOV exists at all.

Part 1 — Why SR-IOV exists

SR-IOV exists because giving many tenants fast, isolated access to one network card in software costs CPU and latency, and handing the whole card to one tenant wastes it. SR-IOV splits the card in hardware instead.

1.1 The problem: one card, many tenants

A server has a few network ports but runs dozens of VMs or hundreds of pods. Each one wants its own network interface. There are four ways to give it one, from slowest to fastest:

Approach How packets travel Speed Isolation Live migration / flexibility
Emulation (e.g. QEMU e1000) the hypervisor pretends to be a real card, register by register slow: every packet traps into the hypervisor good easy
Paravirtual (virtio-net, veth + bridge, OVS) a shared-memory ring to a software switch in the host kernel good, but every packet costs host CPU good easy
Full passthrough (VFIO) the guest owns the whole physical card line rate perfect none: one tenant per card
SR-IOV each tenant owns a VF; the NIC's built-in switch forwards in hardware close to line rate, almost no host CPU hardware-enforced limited: the tenant is tied to that host's NIC

SR-IOV takes the speed of passthrough and shares it: the card itself becomes the switch.

1.2 Where it sits among Kubernetes networking options

A pod's normal interface (eth0) comes from the cluster CNI (Calico, Cilium, OVN-Kubernetes): a veth pair into the host's network stack, often with an overlay. That's great for HTTP and service discovery, and slow for moving gigabytes. The alternatives for a second, fast interface:

Option What the pod gets Kernel bypass possible? Typical use
macvlan / ipvlan a software sub-interface of a host NIC no simple L2 access, low overhead
OVS / OVS-DPDK a port on a software switch with DPDK, on the host side NFV, SDN
SR-IOV VF (netdevice) a real hardware function, kernel driver yes, with RDMA on the VF AI/HPC (RDMA), low-latency apps
SR-IOV VF (vfio-pci) raw device for a user-space driver yes, DPDK telco packet processing, VMs (KubeVirt)
Shared RDMA device the whole host NIC's RDMA device, shared yes, RDMA simple RDMA setups with less isolation

1.3 Why AI clusters use it

Distributed training and disaggregated inference move huge blocks of GPU memory between machines: an all-reduce every step, or 1.2 GB of KV cache per long prompt. That traffic wants RDMA: the NIC moves data straight between GPU memories with no CPU copies. On Kubernetes, the cleanest way to give each pod its own RDMA-capable NIC, with its own address and hardware isolation, is an SR-IOV VF with RDMA enabled. The NVIDIA Network Operator, the SR-IOV Network Operator and llm-d's guides all build on this.

The trade-offs to know (interviewers ask):

  • Fixed capacity. A port supports a limited number of VFs (often 8–127, set in firmware), so VFs are a scarce, schedulable resource, like GPUs.
  • No live migration of a VM with a VF attached (the VF is tied to that physical card), unless you add a fallback such as a virtio failover pair.
  • The NIC is the switch. Traffic between two VFs on the same port turns around inside the NIC, never touching the host's firewall rules or Kubernetes NetworkPolicy. Security moves to VF settings (spoof check, VLAN, trust) and the fabric.
  • Changing the VF count can disrupt the port. On many NICs you must set it to 0 before changing it, and some firmware settings need a reboot. That's why the Kubernetes operator drains nodes.

Check: without looking, say in one sentence each how virtio, passthrough and SR-IOV differ in who moves the packets.

Part 2 — How SR-IOV works in hardware

A VF is a real PCIe function with its own address, queues and interrupts; the PF creates it, the NIC's built-in switch forwards its traffic, and the CPU's IOMMU makes sure it can only touch the memory it was given. Those three pieces (function, switch, IOMMU) are the whole story.

2.1 PCIe in five minutes

Every device on PCIe has an address called a BDF: domain:bus:device.function, e.g. 0000:3b:00.0. Run lspci and each line is one function. A dual-port NIC usually shows two functions, 3b:00.0 and 3b:00.1, one per port.

Each function has a small config space: its vendor ID (8086 Intel, 15b3 NVIDIA/Mellanox), device ID, the memory windows (BARs) the driver maps, and a list of capabilities (MSI-X interrupts, power management, SR-IOV...). lspci -nn shows the IDs; lspci -vvv -s 3b:00.0 shows the capabilities.

2.2 PF and VF

  • The PF is a complete device. Its driver (mlx5_core, ice, i40e, igb) configures the port, the link, the firmware and the eSwitch, and it can create VFs.
  • A VF is a stripped-down function. It has its own config space, BARs, transmit/receive queues and MSI-X interrupts, so a driver can send and receive packets on it directly. It cannot change the link, the firmware, or anyone else's settings. Its VF driver (mlx5_core again for ConnectX, iavf for Intel E810/X710, igbvf for 82576) is often a different, smaller driver.
  • Because a VF has its own queues and interrupts, data never passes through the PF driver or the host CPU on the fast path. That's the speed.

2.3 The SR-IOV capability

The PF's config space carries an SR-IOV capability block. lspci -vvv prints it roughly like this (an illustrative 82576-style example; the numbers differ per card):

Capabilities: [160 v1] Single Root I/O Virtualization (SR-IOV)
        IOVCap: Migration-, Interrupt Message Number: 000
        IOVCtl: Enable- Migration- Interrupt- MSE- ARIHierarchy-
        Initial VFs: 8, Total VFs: 8, Number of VFs: 0, Function Dependency Link: 00
        VF offset: 128, stride: 2, Device ID: 10ca
Field Meaning
Total VFs the most VFs this PF can create (set by firmware)
Number of VFs how many exist right now; Linux writes it when you write sriov_numvfs
VF offset, stride where the VFs' addresses start relative to the PF, and the gap between them
Device ID the PCI device ID every VF of this PF reports (e.g. 10ca for an 82576 VF, 1018 for a ConnectX-5 VF)
VF Enable (in IOVCtl) the switch that actually creates the VFs on the bus

You'll never write these registers by hand: the kernel does it when you write to sysfs (Part 4). But reading them tells you whether a card supports SR-IOV and how many VFs it can make.

ARI. Classic PCIe allows only 8 functions per device. With ARI (Alternative Routing-ID Interpretation), the device and function fields merge, so one card can have up to 256 functions: that's how a port gets 64 or 127 VFs. ARI must be supported by the card and by the PCIe port above it; most server platforms do.

2.4 The eSwitch: the NIC is the switch

Inside an SR-IOV NIC sits a small Ethernet switch (the eSwitch). It connects the physical port (the wire), the PF and every VF. A packet from VF 3 to VF 5 on the same port turns around inside the NIC; a packet to another machine goes out the wire.

It runs in one of two modes:

Mode Who decides where packets go Used for
legacy (default) simple rules per VF: its MAC address, VLAN, spoof check, rate limit, set with ip link set <pf> vf N ... Kubernetes SR-IOV CNI, RDMA pods, most AI clusters
switchdev Linux: each VF gets a representor netdev on the host, and you program forwarding with OVS or TC flower rules, which the NIC offloads to hardware OVS hardware offload, OVN-Kubernetes "smart NIC" mode, NFV

This guide uses legacy mode, as do the RDMA walkthrough and the NVIDIA Network Operator's default SR-IOV setup.

Read it bottom-up: the wire meets the eSwitch, the eSwitch feeds the PF and each VF, and each function's DMA crosses the IOMMU before it touches memory owned by the host, a pod or a VM.

2.5 The IOMMU: why a VF can't read your memory

A VF does DMA: it reads and writes memory by itself. If a pod or VM could point its VF at any physical address, it could read the host's secrets. The IOMMU (Intel VT-d, AMD-Vi) sits between devices and RAM and translates every device address through a page table the kernel controls, so each device can only reach the memory mapped for it.

  • For a VF used as a normal netdevice in a pod, the host kernel still owns the driver, so the IOMMU isn't strictly required for safety; creating VFs doesn't strictly need it either, but vfio-pci does, and vendors and the operators expect it on.
  • For a VF handed to a VM or DPDK through vfio-pci, the IOMMU is mandatory: it's what makes giving raw hardware to an untrusted guest safe.
  • iommu=pt (passthrough) tells Linux to skip translation for devices the host kernel drives itself, which avoids a performance cost for ordinary drivers while keeping isolation for VFIO devices.

IOMMU groups and ACS. The IOMMU can only isolate devices that can't talk to each other directly. If two devices sit behind a PCIe switch that lets them send traffic to each other without going up to the CPU, they share an IOMMU group, and VFIO hands out only whole groups. ACS on the switch forces that traffic up through the IOMMU, so devices land in separate groups. For GPUDirect RDMA it's the opposite trade-off: you want the NIC and GPU to talk directly through the PCIe switch, so GPU servers often turn ACS off (Part 9).

2.6 What a VF is not allowed to do

The PF controls these limits for each VF (defaults vary by driver, so always read them back with ip link show):

  • Spoof check (on by default with Intel drivers, off by default on ConnectX/mlx5): when on, the VF may only send frames with its own MAC address.
  • Trust (off by default): an untrusted VF can't turn on promiscuous mode or set many multicast addresses.
  • VLAN: the PF can force a VLAN tag on everything the VF sends and receives, invisibly to the VF.
  • Rate limits: optional minimum and maximum transmit rates.
  • Link state: the PF can force a VF's link up, down, or follow the physical port (auto).

These are the knobs Kubernetes' SR-IOV CNI sets for you from the network definition (Part 6).

Check: on any Linux machine, run lspci -nn | grep -i ether and find a vendor and device ID; on a server, run sudo lspci -vvv -s <BDF> | grep -A4 SR-IOV and read Total VFs.

Part 3 — Preparing a Linux machine

Four layers must all say yes before a VF can exist: the BIOS, the NIC firmware, the kernel command line, and the driver. Most "SR-IOV doesn't work" tickets are one of these four. Check them in this order, on every node.

3.1 BIOS / UEFI

In the server's setup screen (or its BMC web UI), enable:

Setting Typical name Why
CPU virtualization for I/O Intel VT-d, AMD IOMMU / AMD-Vi the IOMMU (Part 2.5)
SR-IOV support "SR-IOV Global Enable", sometimes per slot lets the platform assign bus numbers and memory for VFs
ARI "ARI Forwarding" / "PCIe ARI Support" more than 8 functions per card
Above 4G decoding "Above 4G Decoding", "MMIO above 4G" room for all VF BARs (and GPU BARs) in the memory map

Names vary by vendor; look them up in your server's manual. Changing them needs a reboot.

3.2 NIC firmware: how many VFs may exist

Some NICs decide the maximum VF count in firmware. NVIDIA ConnectX cards store it in non-volatile settings, changed with mlxconfig (from the MFT tools package) or its open-source twin mstconfig:

sudo mstconfig -d 0000:3b:00.0 query | grep -E "SRIOV_EN|NUM_OF_VFS|LINK_TYPE"
sudo mstconfig -y -d 0000:3b:00.0 set SRIOV_EN=1 NUM_OF_VFS=16   # -y: don't ask for confirmation
# the new values apply after a cold reboot (or a firmware reset: mstfwreset with mstflint, mlxfwreset with MFT)
  • SRIOV_EN=1 turns SR-IOV on; NUM_OF_VFS is the most VFs the firmware will offer (what sysfs later shows as sriov_totalvfs).
  • LINK_TYPE_P1 says whether port 1 is Ethernet (2) or InfiniBand (1). RoCE needs Ethernet.
  • This is exactly what the SR-IOV Network Operator does for you on ConnectX cards, and why it may reboot a node (Part 8).

Intel E810/X710 cards don't need a firmware step; the maximum comes from the driver and the card.

3.3 Kernel command line: turn the IOMMU on

AMD systems usually enable the IOMMU by default. Intel systems often need intel_iommu=on. Most guides add iommu=pt as well, so devices driven by the host kernel skip translation (Part 2.5).

# Debian/Ubuntu: edit /etc/default/grub, add to GRUB_CMDLINE_LINUX:
#   intel_iommu=on iommu=pt        (Intel)        or   iommu=pt   (AMD)
sudo update-grub && sudo reboot
# RHEL/Fedora:
sudo grubby --update-kernel=ALL --args="intel_iommu=on iommu=pt" && sudo reboot

After the reboot, check:

cat /proc/cmdline                                   # your flags are there
sudo dmesg | grep -i -E "DMAR|IOMMU|AMD-Vi" | head  # e.g. "DMAR: IOMMU enabled"
ls /sys/kernel/iommu_groups | wc -l                 # more than 0 groups = IOMMU active

3.4 Drivers and tools

  • PF driver loaded: ethtool -i <pf-interface> shows driver: mlx5_core (ConnectX), ice (E810), i40e (X710) or igb (82576). The in-box kernel drivers support SR-IOV on all of these. For ConnectX you may instead install NVIDIA's DOCA-OFED stack, which the Network Operator can run as a container.
  • RDMA user space (for Part 4.5): rdma-core, ibverbs-utils (gives ibv_devices, ibv_devinfo) and perftest (gives ib_write_bw).
  • Handy tools: pciutils (lspci), iproute2 (ip, rdma, devlink), ethtool, driverctl (to bind VFs to vfio-pci permanently).

3.5 Find the right port

A GPU server may have a management NIC and several data NICs. Never create VFs on the port that carries the node's SSH and Kubernetes traffic unless you mean to.

ip -br link                                       # interface names and state
for i in /sys/class/net/*/device/sriov_totalvfs; do echo "$i: $(cat $i)"; done   # which ports can do SR-IOV
ethtool <iface> | grep -E "Speed|Link detected"   # speed and cable
cat /sys/class/net/<iface>/device/numa_node      # which CPU socket it hangs off (Part 9)
rdma link 2>/dev/null                              # RDMA device behind each port, e.g. mlx5_0/1 -> ens1f0np0

Check: for your chosen port you can write down five facts: its interface name, PCI address, driver, sriov_totalvfs (more than 0), and NUMA node. And ls /sys/kernel/iommu_groups is not empty.

Part 4 — Creating and configuring VFs by hand

On Linux you create VFs by writing a number to one sysfs file, configure them with ip link set <pf> vf N, and give one to a "pod" by moving it into a network namespace. Do this once by hand and the whole Kubernetes stack in Parts 6–8 becomes obvious: it automates exactly these commands.

In the examples the PF interface is ens1f0np0 at 0000:3b:00.0. Use your own names from Part 3.5 (or the lab VM's, Part 5).

4.1 Create VFs

PF=ens1f0np0
cat /sys/class/net/$PF/device/sriov_totalvfs        # the maximum, e.g. 16
echo 4 | sudo tee /sys/class/net/$PF/device/sriov_numvfs
ls -l /sys/class/net/$PF/device/virtfn*             # virtfn0..3 -> the VFs' PCI addresses
lspci -nn | grep -i "virtual function"              # four new PCI functions
ip link show $PF                                    # one "vf N" line per VF

Two rules that catch everyone:

  • To change the number, go through 0: echo 0 > sriov_numvfs, then the new number. Writing 8 when 4 exist fails with "Device or resource busy".
  • Setting it to 0 destroys every VF, including ones in use by pods or VMs. On a live node that's an outage, which is why the operator drains first.

The kernel binds each new VF to its VF driver straight away (unless sriov_drivers_autoprobe is 0), so new network interfaces appear. Find a VF's interface name from its PCI address:

VF0=$(basename $(readlink /sys/class/net/$PF/device/virtfn0))   # e.g. 0000:3b:00.2
ls /sys/bus/pci/devices/$VF0/net/                                # e.g. ens1f0v0

4.2 Configure a VF from the PF

All VF settings live on the PF (the VF can't change them itself):

sudo ip link set $PF vf 0 mac 02:00:00:00:00:10   # fixed MAC (otherwise random or zero)
sudo ip link set $PF vf 0 vlan 100                # tag everything this VF sends with VLAN 100, invisibly
sudo ip link set $PF vf 0 spoofchk on             # may only send from its own MAC (default on for Intel, off for mlx5)
sudo ip link set $PF vf 0 trust off               # no promiscuous mode for this VF (default off)
sudo ip link set $PF vf 0 max_tx_rate 10000       # cap at 10,000 Mb/s (support varies by NIC)
sudo ip link set $PF vf 0 state auto              # follow the physical link (enable = always up, for tests)
ip link show $PF                                  # read it all back

The ip link show line for a VF reads like: vf 0 link/ether 02:00:00:00:00:10 ..., vlan 100, spoof checking on, link-state auto, trust off. This is precisely what SR-IOV CNI sets from a network definition's vlan, spoofchk and trust fields.

4.3 Give a VF to a "pod": network namespaces

A pod is, for networking, a network namespace. Moving a VF's interface into one is the core of what SR-IOV CNI does:

VFNET=$(ls /sys/bus/pci/devices/$VF0/net/)
sudo ip netns add podA
sudo ip link set $VFNET netns podA                     # the interface disappears from the host...
sudo ip netns exec podA ip link set $VFNET name net1    # ...and renamed, as SR-IOV CNI does with the name Multus picks
sudo ip netns exec podA ip addr add 192.168.50.10/24 dev net1
sudo ip netns exec podA ip link set net1 up
sudo ip netns exec podA ip -br addr                     # podA sees only lo and net1

First make the VLANs match: VFs on different VLANs can't reach each other, and 4.2 put VF 0 on VLAN 100. Either give VF 1 the same VLAN (sudo ip link set $PF vf 1 vlan 100) or clear VF 0's (sudo ip link set $PF vf 0 vlan 0). Then repeat with VF 1 into podB at 192.168.50.11, then sudo ip netns exec podA ping -c3 192.168.50.11. The ping turns around inside the NIC's eSwitch: it never touches the host's bridge or iptables. (If the port has no cable, set state enable on both VFs so their links come up.)

To undo: sudo ip netns del podA returns the VF's interface to the host (still named net1).

4.4 netdevice or vfio-pci?

A VF can be driven two ways:

Driver What you get Used by
VF kernel driver (iavf, mlx5_core, igbvf) a normal network interface (and an RDMA device on ConnectX) pods with RDMA or plain sockets; this guide
vfio-pci raw PCI access from user space, protected by the IOMMU DPDK apps, KubeVirt VMs 
sudo modprobe vfio-pci
sudo driverctl set-override $VF0 vfio-pci          # rebinds now and after reboots
ls -l /sys/bus/pci/devices/$VF0/driver             # -> vfio-pci
sudo driverctl unset-override $VF0                 # back to the normal driver

One ConnectX detail: DPDK on ConnectX does not use vfio-pci. Its mlx5 driver works alongside the kernel driver ("bifurcated"), so ConnectX VFs stay on mlx5_core even for DPDK.

4.5 RDMA on a VF

On ConnectX, with the mlx5_ib module loaded, every VF also gets an RDMA device:

ls /sys/bus/pci/devices/$VF0/infiniband/     # e.g. mlx5_4
rdma link                                     # mlx5_4/1 ... netdev ens1f0v0
ibv_devinfo -d mlx5_4 | grep -E "state|link_layer"

Here's a subtlety that matters for containers. An RDMA device is not a network interface, so moving the netdev into a namespace does not move its RDMA device. Linux has two modes:

rdma system netns mode What a namespace can see Who uses it
shared (default) every RDMA device on the host simple setups; weaker isolation
exclusive only the RDMA devices moved into it Kubernetes with SR-IOV + RDMA CNI (Part 6.5) 
rdma system                              # "netns shared" or "netns exclusive"
# the kernel only switches modes while NO extra network namespaces exist, so:
sudo ip netns del podA; sudo ip netns del podB   # delete every namespace first
sudo rdma system set netns exclusive
sudo ip netns add podA                    # recreate it, move the VF in again (4.3)
sudo rdma dev set mlx5_4 netns podA       # what RDMA CNI does for a pod
# on a Kubernetes node (always full of pod namespaces) set it at boot instead, then reboot:
#   echo "options ib_core netns_mode=0" | sudo tee /etc/modprobe.d/ib_core.conf
#   (rebuild the initramfs too if ib_core loads from it: update-initramfs -u / dracut -f)

The operator can set this mode for you (Part 8.3). With exclusive mode, two pods on the same node can't see each other's RDMA devices or counters.

4.6 Make it survive a reboot

sriov_numvfs resets to 0 at every boot. Outside Kubernetes, pick one way to restore it:

  • udev rule (runs when the PF appears; match it by PCI address, because at the add event the interface still has its kernel name, not ens1f0np0): /etc/udev/rules.d/70-sriov.rules with ACTION=="add", SUBSYSTEM=="net", KERNELS=="0000:3b:00.0", ATTR{device/sriov_numvfs}="4".
  • NetworkManager: nmcli connection modify <pf-connection> sriov.total-vfs 4, which also stores per-VF settings.
  • A systemd one-shot unit that runs your Part 4.1 and 4.2 commands after the network driver loads.

On Kubernetes, don't do any of these yourself: the SR-IOV operator's config daemon re-applies the policy at every boot.

4.7 switchdev mode, briefly

In switchdev mode (Part 2.4), each VF gets a representor interface on the host (names like ens1f0npf0vf0). Traffic the eSwitch can't handle goes to the representor, where OVS or TC rules decide, and the NIC then offloads matching flows to hardware.

sudo devlink dev eswitch show pci/0000:3b:00.0              # mode legacy
sudo devlink dev eswitch set pci/0000:3b:00.0 mode switchdev # usually with sriov_numvfs at 0 first

You need this for OVS hardware offload or OVN-Kubernetes on smart NICs, not for the RDMA setups in this guide.

Part 5 — Lab A: SR-IOV without hardware

5.4 RDMA tools with Soft-RoCE

igb has no RDMA, but Linux has a software RDMA driver, rxe (Soft-RoCE), that runs RoCE v2 on top of any Ethernet interface. It's slow, but every RDMA command and concept works: devices, GIDs, ibv_devinfo, ib_write_bw, and netns modes.

sudo apt install -y rdma-core ibverbs-utils perftest linux-modules-extra-$(uname -r)
sudo modprobe rdma_rxe
sudo rdma link add rxe0 type rxe netdev $PF        # an RDMA device on the PF
rdma link                                          # link rxe0/1 state ACTIVE ... netdev enp1s0
ibv_devinfo -d rxe0 | grep -E "state|link_layer"   # PORT_ACTIVE, Ethernet
ibv_devinfo -v -d rxe0 | grep GID                  # the GID table (Part 1.2 of the RDMA walkthrough)
# bandwidth test over loopback: server in one terminal, client in another
ib_write_bw -d rxe0
ib_write_bw -d rxe0 localhost

Check: ib_write_bw prints a bandwidth table. The number is small (a few Gb/s at most): Soft-RoCE uses the CPU, which is exactly the cost real RDMA hardware removes. Also try rdma system to see the netns mode from Part 4.5.

Part 6 — Kubernetes building blocks

Kubernetes splits SR-IOV into two jobs: a device plugin that counts and hands out VFs like GPUs, and a chain of CNI plugins (Multus, then SR-IOV CNI, then optionally RDMA CNI) that wires the chosen VF into the pod. Every piece maps to a command you ran in Part 4.

Part 4 command Kubernetes piece that does it
echo N > sriov_numvfs, firmware, persistence you, or the SR-IOV Network Operator's config daemon (Part 8)
"which VFs are free on this node?" SR-IOV network device plugin
ip link set <pf> vf N mac/vlan/spoofchk/trust SR-IOV CNI
ip link set <vf> netns <pod>, rename to net1, add IP SR-IOV CNI + an IPAM plugin
a second interface at all Multus + a NetworkAttachmentDefinition
rdma dev set <dev> netns <pod> RDMA CNI
keep CPU, GPU and VF on one socket kubelet Topology Manager

Step 8 belongs in the chain only when the host's RDMA mode is exclusive; in shared mode leave RDMA CNI out. Sections 6.1–6.5 explain each lane in turn.

6.1 The SR-IOV network device plugin

A device plugin is a small daemon per node that tells the kubelet "I have N of resource X" and, when a pod is admitted, "give it this one". The SR-IOV plugin reads a config listing resource pools, each with selectors that pick VFs:

{
  "resourceList": [{
    "resourceName": "sriov_rdma",
    "resourcePrefix": "nvidia.com",
    "selectors": [{
      "vendors": ["15b3"],
      "pfNames": ["ens1f0np0#0-7"],
      "isRdma": true
    }]
  }]
}
  • Selectors you'll use: vendors, devices (VF device IDs), drivers, pfNames (with an optional #first-last VF range), rootDevices (PF PCI addresses), linkTypes (ether, infiniband), isRdma (also mount the VF's RDMA device files), needVhostNet.
  • The result is a node resource, e.g. nvidia.com/sriov_rdma: 8, visible in kubectl describe node under Allocatable. The default prefix, if you don't set one, is intel.com.
  • When the kubelet admits a pod that requests one, the kubelet chooses a free VF from those the plugin advertised and calls the plugin's Allocate with it; the plugin answers with an environment variable named after the resource, holding the VF's PCI address: PCIDEVICE_NVIDIA_COM_SRIOV_RDMA=0000:3b:00.3. With isRdma, it also mounts that VF's /dev/infiniband/* files into the container.
  • It also reports each VF's NUMA node, which the Topology Manager uses (6.6).

6.2 Multus and the NetworkAttachmentDefinition

Kubernetes itself gives a pod exactly one network. Multus is installed as the node's main CNI and delegates: it calls the cluster's normal CNI for eth0, then reads the pod's annotation and calls one more CNI per extra network (net1, net2, ...).

Each extra network is a NetworkAttachmentDefinition (NAD): a namespaced object whose spec.config is a CNI config, plus an annotation saying which device-plugin resource it needs:

apiVersion: k8s.cni.cncf.io/v1
kind: NetworkAttachmentDefinition
metadata:
  name: sriov-net
  namespace: demo
  annotations:
    k8s.v1.cni.cncf.io/resourceName: nvidia.com/sriov_rdma
spec:
  config: '{
    "cniVersion": "0.3.1", "name": "sriov-net", "type": "sriov",
    "vlan": 100, "spoofchk": "on", "trust": "off",
    "ipam": {"type": "whereabouts", "range": "192.168.50.0/24"}
  }'

A pod opts in with an annotation and a resource request:

metadata:
  annotations:
    k8s.v1.cni.cncf.io/networks: sriov-net
spec:
  containers:
  - name: app
    resources:
      limits:
        nvidia.com/sriov_rdma: "1"

After it starts, Multus writes what it did into the pod's k8s.v1.cni.cncf.io/network-status annotation (interface, IPs, and the VF's PCI address): the first thing to read when debugging.

6.3 SR-IOV CNI

Given the VF's PCI address (Multus passes it as deviceID, taken from the device plugin's allocation), SR-IOV CNI does Part 4.2 and 4.3: it sets MAC, VLAN, spoof check, trust and rate limits on the PF for that VF, moves the VF's interface into the pod's namespace, renames it, calls the IPAM plugin, and brings it up. On pod deletion it moves the VF back and resets its settings. For vfio-pci VFs it skips the interface part: the app (DPDK, a VM) drives the device itself.

6.4 IPAM: who hands out addresses on net1

IPAM plugin Scope Watch out
host-local one node two nodes can hand out the same IP; only for single-node tests
whereabouts whole cluster needs its CRDs; a common default
nv-ipam whole cluster, per-node blocks NVIDIA Network Operator's choice; ranges in IPPool objects
static per pod addresses in the IPAM config, or per pod in the network annotation when the NAD sets "capabilities": {"ips": true}

6.5 RDMA CNI

When the host's RDMA netns mode is exclusive (Part 4.5), moving the netdev isn't enough: the pod also needs its RDMA device. RDMA CNI runs chained after SR-IOV CNI and moves the VF's RDMA device into the pod's namespace. You add it to the NAD's config as a plugin list ("plugins": [{"type": "sriov", ...}, {"type": "rdma"}]). In shared mode you must leave it out of the chain (it fails there), and every pod can see every RDMA device.

6.6 Topology Manager: keep it on one socket

A pod with a GPU on socket 0 and a VF on socket 1 sends every byte across the CPU interconnect, which can cost a large share of bandwidth. The kubelet's Topology Manager lines up CPUs and devices on one NUMA node:

  • kubelet settings: topologyManagerPolicy: single-numa-node (or restricted), usually with cpuManagerPolicy: static.
  • the pod must be Guaranteed QoS (requests equal limits, whole CPUs) for CPU pinning to apply.
  • device plugins report each device's NUMA node; if no single node can satisfy CPU + GPU + VF, the pod is rejected (TopologyAffinityError) instead of being placed badly.

Rail-optimised GPU servers (one NIC per GPU, under the same PCIe switch) make this easy: pick the VF from the NIC next to your GPU.

SriovNetworkNodePolicy: which NICs, how many VFs, which driver, and the resource name.

apiVersion: sriovnetwork.openshift.io/v1
kind: SriovNetworkNodePolicy
metadata:
  name: rdma-vfs
  namespace: sriov-network-operator
spec:
  resourceName: sriov_rdma            # pods ask for openshift.io/sriov_rdma (upstream default prefix; nvidia.com under the NVIDIA Network Operator)
  nodeSelector:
    feature.node.kubernetes.io/pci-15b3.present: "true"   # set by Node Feature Discovery; without NFD use your own node label

  mtu: 9000
  priority: 90                        # lower number wins when policies overlap

  trust: "off"
  ipam: '{"type": "whereabouts", "range": "192.168.50.0/24"}'

One SriovNetwork makes a NAD in one namespace. Pods in another namespace need a second SriovNetwork (that's why the RDMA walkthrough has sriov-network-llmd.yaml for llm-d's namespace). For InfiniBand use SriovIBNetwork instead.

SriovOperatorConfig (default): global settings, such as which nodes run the config daemon, webhooks, and log level. SriovNetworkPoolConfig: groups nodes so changes roll out with a maxUnavailable budget, and sets the host's RDMA mode (rdmaMode: exclusive or shared, Part 4.5).

8.3 Drains and reboots: the part that surprises people

When a policy changes a node, the config daemon may need to destroy existing VFs (numVfs must go through 0), change NIC firmware, or change the RDMA mode. So it:

  1. cordons and drains the node (evicts pods), unless draining is disabled;
  2. applies the change, and reboots if firmware or kernel settings require it (ConnectX SRIOV_EN/NUM_OF_VFS changes, RDMA mode changes);
  3. reports syncStatus: Succeeded and uncordons.

By default it does this one node at a time; SriovNetworkPoolConfig.maxUnavailable lets you go faster. On a GPU cluster that means a new policy can drain every GPU node in turn, so apply policy changes in a maintenance window, and pick numVfs generously up front so you rarely change it.

8.4 The NVIDIA Network Operator

On NVIDIA networking, most teams install the NVIDIA Network Operator instead. It deploys the SR-IOV Network Operator (sriovNetworkOperator.enabled=true) and, from one NicClusterPolicy, also Multus, the standard CNI plugins, nv-ipam, the RDMA shared device plugin (an alternative to VFs), and optionally the DOCA-OFED driver container. The VF resource prefix becomes nvidia.com.

Part 9 — Performance and placement

A VF can only go as fast as the slowest thing between the wire and your memory: the PCIe link, the CPU socket it hangs off, the MTU, and, for GPUs, whether the NIC can reach GPU memory directly. Measure each before blaming the application.

9.1 Measure the ceiling first

All VFs on a port share that port's bandwidth: 8 VFs on a 200 Gb/s port don't get 200 Gb/s each. Measure one VF, then several at once, between two nodes:

Tool Measures Expect (healthy)
ib_write_bw -d <vf-rdma-dev> -s 1048576 -D 10 --report_gbits RDMA bandwidth, large messages about 90% of line rate, e.g. 185–195 Gb/s on 200 Gb/s
ib_write_lat RDMA latency a few microseconds
ib_write_bw ... --use_cuda=0 GPUDirect RDMA (GPU memory to GPU memory) close to the host-memory number
iperf3 -P 8 over the VF TCP on the same wire well below RDMA; costs CPU

The RDMA walkthrough's network-tests/run_network_tests.sh runs all of these between two pods with VFs.

9.2 PCIe link

A 200 Gb/s port needs a PCIe Gen4 x16 slot; a card that trained down to x8 or Gen3 loses half its bandwidth without any error.

sudo lspci -vv -s <pf-bdf> | grep -E "LnkCap:|LnkSta:"   # LnkSta should match LnkCap (speed and width)

9.3 NUMA: stay on one socket

On a two-socket server, a VF used by a pod whose CPUs or GPU sit on the other socket pays for every byte crossing the inter-socket link.

cat /sys/class/net/<pf>/device/numa_node       # the NIC's socket
nvidia-smi topo -m                            # GPU <-> NIC: PIX/PXB best, NODE ok, SYS bad
lscpu | grep -i numa                          # which CPUs belong to which socket

In Kubernetes, the Topology Manager (Part 6.6) enforces this. Without it, pick VF pools per NIC (pfNames) and keep GPU and VF on matching sockets with node-level knowledge.

9.4 MTU

Jumbo frames (MTU 9000, or 4200 for some RoCE fabrics) mean fewer packets per gigabyte. Three places must agree: the PF (mtu in the node policy), the VF inside the pod (SR-IOV CNI can set it), and every switch port on the path. A mismatch shows up as large transfers stalling while small ones work. For RDMA the relevant number is the RoCE MTU (active_mtu in ibv_devinfo), which is derived from the Ethernet MTU.

9.5 GPUDirect RDMA and ACS

For KV-cache and training traffic, data should flow NIC to GPU through the PCIe switch, never through CPU RAM:

  • the GPU and NIC should share a PCIe switch (PIX/PXB in nvidia-smi topo -m);
  • ACS on that switch should be off (or set to allow peer-to-peer), otherwise every NIC-to-GPU transfer goes up to the CPU's root complex and back, cutting bandwidth;
  • GPUDirect is enabled by DMA-BUF (open GPU kernel modules, Linux 5.12+) or the older nvidia-peermem module; the GPU Operator sets either up.

The trade-off with Part 2.5: ACS off means devices behind that switch share an IOMMU group. That's fine for netdevice VFs in pods, and a problem only if you wanted to pass those devices to separate VMs.

9.6 Interrupts and CPU

With RDMA the CPU barely touches the data path. With plain TCP over a VF, interrupt and softirq load lands on whichever cores handle the VF's queues. Keep them on the NIC's socket (irqbalance usually does; check /proc/interrupts), and give latency-sensitive pods whole, pinned CPUs (Guaranteed QoS with the static CPU manager).

Part 10 — Security and day-2 operations

SR-IOV traffic bypasses the host's software switch, so the host's firewall and Kubernetes NetworkPolicy never see it (unless you add MultiNetworkPolicy, below); isolation comes from VF settings, VLANs and the fabric instead. Plan for that, and for the fact that changing VFs disrupts nodes.

10.1 What protects whom

a pod sends with another machine's MAC or IP spoofchk on (MAC); IP spoofing needs fabric or switch rules SriovNetwork spoofChk
a pod sniffs other traffic trust off (no promiscuous mode) SriovNetwork trust
tenants share an L2 segment a VLAN per tenant or network, enforced by the PF SriovNetwork vlan
one pod floods the port maxTxRate per VF SriovNetwork maxTxRate
a pod reads another pod's RDMA devices or counters RDMA netns mode exclusive + RDMA CNI SriovNetworkPoolConfig rdmaMode

NetworkPolicy does not apply to net1. Calico, Cilium and friends filter traffic on the primary interface. The separate MultiNetworkPolicy API (multi-networkpolicy-iptables) can filter secondary interfaces, including netdevice SR-IOV VFs, but it's an extra component you must deploy, and it doesn't apply to vfio-pci VFs or RDMA traffic, which bypass the kernel. For the SR-IOV network, control who can reach whom with VLANs, separate subnets and switch ACLs, and keep the NAD (the SriovNetwork's networkNamespace) out of namespaces that shouldn't have it.

RDMA pods need IPC_LOCK (to pin memory) and sometimes a raised memlock limit. That's a capability, not full privilege: grant it per workload, and keep privileged: true for the operator's own daemons only.

10.2 Day-2 operations

  • Changing a policy drains nodes (Part 8.3). Batch changes, run them in a maintenance window, and use SriovNetworkPoolConfig.maxUnavailable deliberately.
  • Firmware and driver upgrades (DOCA-OFED container, NIC firmware) restart the NIC driver, which destroys VFs. Drain first; the NVIDIA Network Operator has an upgrade controller that does this node by node.
  • Kernel upgrades can change interface names or driver behaviour; pfNames that no longer match leave a node with 0 VFs. Prefer rootDevices (PCI addresses) when names are unstable.
  • Capacity planning: VFs per node = pods per node that need the fast network. A pod that requests a VF can't schedule when the node runs out, even with free GPUs.
  • Monitoring: watch allocatable vs allocated VFs per node (kubectl describe node), SriovNetworkNodeState.status.syncStatus, NIC port counters (ethtool -S <pf>, RDMA counters under /sys/class/infiniband/<dev>/ports/1/counters), and drops or pause frames on RoCE ports. The SR-IOV operator also has a metrics exporter you can enable.

Check: for one SriovNetwork in your cluster, say which of the risks in 10.1 it protects against and which it doesn't.

Part 12 — Interview questions and model answers

Answer shape: what it is → how it works → the trade-off → how you checked it.

"What is SR-IOV?" A PCIe standard that lets one physical NIC function (the PF) create many lightweight virtual functions (VFs). Each VF has its own PCI address, queues and interrupts, so a VM or pod can drive it directly while the NIC's built-in switch forwards traffic in hardware. You get near line-rate networking with almost no host CPU, at the cost of a fixed number of VFs, no live migration, and isolation that moves from the host's software switch to VF settings and the fabric.

"PF versus VF?" The PF is the full device: it owns the port, the firmware and the eSwitch, and it creates and configures VFs. A VF can send and receive but can't change the link or anyone else's settings; its MAC, VLAN, spoof check, trust and rate limits are set from the PF with ip link set <pf> vf N.

"Why do you need the IOMMU?" VFs do DMA. The IOMMU translates and checks every device address, so a VF given to a VM or DPDK app through vfio-pci can only reach memory mapped for it. Devices that can talk peer-to-peer share an IOMMU group; ACS splits groups. For GPUDirect RDMA you often turn ACS off so the NIC and GPU talk directly, which is fine for netdevice VFs in pods.

"Walk me through how a pod gets an SR-IOV interface." The config daemon (or you) creates VFs. The SR-IOV device plugin advertises them as a resource, say nvidia.com/sriov_rdma: 8. The pod requests one and names a NetworkAttachmentDefinition in an annotation. The scheduler places it on a node with a free VF; the kubelet chooses a free VF and calls the device plugin's Allocate, which returns the PCIDEVICE_ variable with that VF's PCI address (and, for RDMA, the /dev/infiniband mounts). Multus, as the node's CNI, sets up eth0 with the cluster CNI, then calls SR-IOV CNI with that PCI address. SR-IOV CNI applies MAC/VLAN/spoof/trust on the PF, moves the VF into the pod's network namespace as net1, and gets an IP from IPAM. With RDMA in exclusive mode, RDMA CNI then moves the VF's RDMA device in too.

"Why does changing an SR-IOV policy drain my nodes?" Changing the VF count means destroying the existing VFs (the count must go through zero), and on ConnectX cards the maximum lives in firmware, which needs a reboot. Pods using VFs would lose their interfaces, so the operator cordons and drains first, one node at a time unless a pool config allows more.

"NetworkPolicy doesn't block traffic on my SR-IOV network. Why?" Because that traffic never passes the host's network stack: the NIC's eSwitch forwards it. NetworkPolicy implementations filter the primary interface. On net1 you isolate with VLANs, subnets, spoof checking, and switch ACLs, and by limiting which namespaces have the network.

"Shared RDMA device or SR-IOV VFs for RDMA pods?" A shared device plugin hands every pod the same host RDMA device: simple, no VF count limit, but weak isolation and no per-pod address on the fabric. VFs give each pod its own hardware function, its own address and exclusive RDMA namespace, at the cost of VF capacity and drains when policies change. Multi-tenant or production AI clusters usually go with VFs.

"How would you debug a slow RDMA pod?" Bottom-up: PCIe link width and speed (lspci LnkSta), NUMA placement of the NIC versus the pod's CPUs and GPU (nvidia-smi topo -m), MTU on PF, VF and switch, PFC/ECN on the switch for RoCE, then ib_write_bw between two pods to compare with line rate, and GPUDirect with --use_cuda. Only then the application.

"How did you learn this without hardware?" QEMU's emulated igb (Intel 82576) supports SR-IOV, so I created real VFs in a VM, wired them into pods by hand with k3s, Multus, SR-IOV CNI and the device plugin, and used Soft-RoCE for the RDMA tools. Then I applied the same steps with the operator on a GPU cluster with ConnectX NICs.

The pod start-up order in one line (Part 6): scheduler (picks a node with a free VF) → device plugin (allocates a specific VF) → Multus (primary CNI, then the extra network) → SR-IOV CNI (VF settings, move into the pod) → IPAM (address) → RDMA CNI (RDMA device, if exclusive mode).
